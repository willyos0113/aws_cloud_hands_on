## 詳解

## 一、EC2 計價方案

**1.** 答案：**B**

「可隨時中斷、沒有時間限制、成本最低」是 Spot 的典型情境。
易混淆：Standard RI 要承諾期限，不適合這種短期、可中斷的批次工作；Dedicated Hosts 是為了授權與合規，不是為了省錢。

👉 可中斷、省錢 -> Spot。

**2.** 答案：**C**

固定機型家族、連續使用、不會更換，折扣最深的是 Standard RI。
易混淆：Convertible RI 的彈性是用較低的折扣換來的，這題用不到換機型的彈性。

👉 不換機型、折扣最深 -> Standard RI；要換機型 -> Convertible RI（折扣較低）。

**3.** 答案：**A**

只有 Compute Savings Plans 能同時套用在 EC2、Fargate、Lambda，且不限機型家族與 Region。
易混淆：EC2 Instance Savings Plans 綁定特定 Region 與機型家族，也不涵蓋 Fargate、Lambda；Standard RI 只涵蓋 EC2。

👉 跨 EC2 + Fargate + Lambda -> Compute Savings Plans。

**4.** 答案：**D**

要在承諾期間換成不同的機型家族，是 Convertible RI 的特性，代價是折扣比 Standard RI 略低。
易混淆：Standard RI 折扣最深，但不能換機型家族。

👉 要換機型 -> Convertible RI。

**5.** 答案：**B**

要看得到實體插槽與核心數、證明授權合規，只有 Dedicated Hosts。
易混淆：Dedicated Instances 只保證不跟其他客戶共用硬體，看不到插槽與核心數，無法用於這種授權；Capacity Reservations 只是預留容量。

👉 依插槽／核心計價的既有授權 -> Dedicated Hosts。

**6.** 答案：**AB**

Spot 折扣大，被回收前約有 2 分鐘的中斷通知。
易混淆：Spot 隨時可能被回收，所以不保證不被中斷（C），也不適合資料庫主節點（D）；Spot 不需要承諾期限（E），需要承諾的是 RI 與 Savings Plans。

👉 Spot = 折扣大 + 可能被收回（前 2 分鐘警告）+ 不用承諾。

## 二、Well-Architected 與 Cloud Adoption Framework

**7.** 答案：**B**

選對運算資源類型與規模，並隨需求持續評估新服務，是效能效率的設計原則。
易混淆：營運卓越強調自動化、記錄與從失敗中學習；成本最佳化強調消除浪費。

👉 選對資源、持續評估新技術 -> 效能效率。

**8.** 答案：**A**

降低環境衝擊、提高資源使用率與能源效率，是第六個支柱：永續性。
易混淆：成本最佳化雖然也會減少用量，但目的是省錢，不是減碳。

👉 碳足跡、能源效率 -> 永續性（六大支柱：營運卓越、安全、可靠、效能、成本、永續）。

**9.** 答案：**C**

評估上雲準備度、找出人員與流程缺口是 CAF 的用途，它是給「組織」轉型用的。
易混淆：Well-Architected Tool 是針對「單一工作負載」的架構做檢視與評分，名字相似但對象不同。

👉 組織上雲準備度（readiness）-> CAF；工作負載架構檢視 -> Well-Architected。

**10.** 答案：**AC**

平台視角包含平台架構、資料架構、資料工程、佈建與編配、現代化應用程式開發、CI/CD。
易混淆：事件回應屬於安全視角、風險管理屬於治理視角、雲端熟練度屬於人員視角。

👉 平台視角 -> CI/CD、資料工程、佈建、應用開發。

**11.** 答案：**D**

小幅調整以享受雲端優勢（例如改用託管資料庫）是 Replatform，又稱 lift-tinker-and-shift。
易混淆：Rehost 是原封不動搬；Refactor 是重新設計架構（例如拆微服務）；Retire 是淘汰不用的系統。

👉 自建 DB 改託管 DB、程式不大改 -> Replatform。

## 三、ELB、Auto Scaling、Route 53 與 Global Accelerator

**12.** 答案：**C**

Auto Scaling 群組關聯 target group 後，啟動的執行個體會自動註冊，終止前會自動移除。
易混淆：增減 EC2 的是 Auto Scaling，不是 ALB；target group 與 Auto Scaling 群組是各自獨立的資源，靠「關聯」連在一起。

👉 ASG 負責增減機器，target group 負責流量目標，關聯後自動註冊／移除。

**13.** 答案：**D**

依 HTTP 路徑（第七層）做路由是 ALB 的功能。
易混淆：NLB 運作在第四層（TCP/UDP），看不到 HTTP 路徑；Gateway Load Balancer 用來掛載第三方虛擬防火牆等設備。

👉 HTTP／路徑路由／第七層 -> ALB。

**14.** 答案：**A**

每秒數百萬連線、極低延遲、固定靜態 IP 是 NLB（第四層）的特色。
易混淆：ALB 不提供固定靜態 IP，且針對 HTTP/HTTPS；Route 53 是 DNS，不處理連線。

👉 TCP/UDP、極高效能、靜態 IP -> NLB。

**15.** 答案：**B**

Route 53 可用延遲、健康檢查、容錯移轉等路由策略，在 DNS 層把使用者導向不同 Region。
易混淆：CloudFront 是內容快取的 CDN；ALB 只活在單一 Region；S3 Transfer Acceleration 是加速上傳到 S3。

👉 跨 Region 的 DNS 導流／容錯移轉 -> Route 53。

**16.** 答案：**C**

Global Accelerator 提供兩組靜態 Anycast IP，流量從最近的邊緣進入 AWS 骨幹，再導向多個 Region 的端點（ALB、NLB、EC2 等）。
易混淆：Route 53 只回覆 DNS 答案，流量不經過它，也沒有固定入口 IP；CloudFront 是快取內容。

👉 固定 Anycast IP + 走 AWS 骨幹 + 多 Region 端點 -> Global Accelerator。

## 四、S3 儲存類別

**17.** 答案：**B**

存取模式不確定、希望自動依存取頻率調整層級 -> Intelligent-Tiering。
易混淆：Standard-IA、One Zone-IA 是你「預先決定」層級，不會自動調整。

👉 存取模式不明／混合 -> Intelligent-Tiering。

**18.** 答案：**D**

可重新產生、很少存取、可接受單一 AZ -> One Zone-IA。
易混淆：Glacier Flexible Retrieval 是封存用，取回要等；One Zone-IA 取回是毫秒級。

👉 可重新產生、很少存取、單一 AZ -> One Zone-IA。

**19.** 答案：**A**

長期保存、幾乎不取回、能接受 12 小時以上、成本最低 -> Glacier Deep Archive。
易混淆：Flexible Retrieval 的取回時間為數分鐘到 12 小時（Bulk 在 12 小時內），成本比 Deep Archive 高。

👉 Deep Archive：12 小時以上、最便宜；Flexible Retrieval：5 分鐘～12 小時。

**20.** 答案：**C**

很少存取（約每季一次）但需要毫秒級取回 -> Glacier Instant Retrieval。
易混淆：Flexible Retrieval 與 Deep Archive 都需要等待取回；只有 Instant Retrieval 是毫秒級。

👉 封存級成本 + 毫秒取回 -> Glacier Instant Retrieval。

**21.** 答案：**BD**

S3 儲存總容量實質上沒有上限；S3 Standard 的資料會自動分散在 Region 內多個 AZ。
易混淆：S3 不需預先配置容量（A 是 EBS 的思維）；S3 不能指定存放在哪個 AZ（C），這也是 One Zone-IA 以外不能選 AZ 的原因；5 GB 是錯的，單一物件最大為 5 TB。

👉 S3：不用預配容量、不能選 AZ、Standard 跨多 AZ。

## 五、身分與存取

**22.** 答案：**B**

已有外部 IdP、要單一登入多個 AWS 帳戶 -> IAM Identity Center。
易混淆：Cognito 是給「應用程式的終端使用者」用的，不是給員工登入 AWS 帳戶；IAM 使用者就是要再建一組帳密。

👉 員工 + 既有 IdP + 多帳戶 SSO -> Identity Center。

**23.** 答案：**D**

App 終端使用者的註冊、登入、社群帳號登入 -> Cognito。
易混淆：Identity Center 管的是員工對 AWS 帳戶與應用的存取，不是 App 的客戶。

👉 App 層級的使用者驗證 -> Cognito。

**24.** 答案：**C**

列出所有 IAM 使用者的密碼、Access Key、MFA 狀態等 -> credential report。
易混淆：Access Advisor 顯示的是「某身分最近使用了哪些服務」；CloudTrail 記錄 API 呼叫；Config 記錄資源組態變化。

👉 全帳戶 IAM 使用者憑證狀態總表 -> credential report。

**25.** 答案：**B**

SCP 為 Organizations 內的帳戶設定權限上限，即使帳戶管理員也無法超出。
易混淆：許可邊界（Permissions boundary）作用在單一 IAM 使用者或角色，不是整個成員帳戶；SCP 本身不授予權限，只限制上限。

👉 整個成員帳戶的權限上限 -> SCP。

## 六、資料傳輸費用

**26.** 答案：**C**

跨 AZ 的傳輸會收費。
易混淆：傳入 AWS 的流量不收費；同 Region 內 S3 傳到 EC2 不收費；同一個 AZ 內透過私有 IP 的傳輸也不收費。

👉 跨 AZ 要錢；同 AZ 私有 IP 不要錢。

**27.** 答案：**AB**

傳出到網際網路、跨 Region 複製都會收費。
易混淆：傳入 AWS 的流量（C、E）和同 Region 內 S3 傳到 EC2（D）不收費。

👉 進來免費、出去收費；跨 Region、跨 AZ 收費。

## 七、RDS 與 Aurora

**28.** 答案：**A**

同步複寫到另一個 AZ、故障自動容錯移轉 -> Multi-AZ，目的是高可用。
易混淆：讀取複本是「非同步」複寫，主要用來分攤讀取，不以容錯移轉為主要目的。

👉 同步、跨 AZ、自動容錯移轉 -> Multi-AZ。

**29.** 答案：**D**

分攤讀取流量 -> 讀取複本（Read Replica）。
易混淆：Multi-AZ 的備援節點平時不提供讀取流量，目的是高可用，不是效能。

👉 分攤讀取、提升效能 -> Read Replica（非同步）。

**30.** 答案：**B**

用量不固定、閒置時自動縮小容量、相容 MySQL -> Aurora Serverless。
易混淆：DynamoDB 不相容 MySQL；Redshift 是資料倉儲；Multi-AZ 是高可用，不會依用量調整容量。

👉 用量時有時無、自動調整容量、相容 MySQL／PostgreSQL -> Aurora Serverless。

## 作答後怎麼用

1. 先數錯題落在哪一個大類，同一類錯 2 題以上就是這次要補的弱點。
2. 錯題請用自己的話寫出「它跟我選的那個差在哪」，只寫「答案是什麼」的筆記，換個說法就會再錯。
3. 隔天、第 3 天、第 7 天各把錯題重做一次。
