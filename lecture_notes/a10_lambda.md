## 一、從虛擬機到函式：伺服器歸 AWS，你只留程式

**三件事**

- 機器歸 AWS
- 事件來了才跑
- 三種運算型態

**責任線：EC2 vs Lambda**

|            | EC2 虛擬機 | Lambda                     |
| ---------- | ---------- | -------------------------- |
| 程式碼     | 你做       | 你做（`handler` 入口函式） |
| 系統與修補 | 你做       | AWS 做                     |
| 擴縮       | 你做       | AWS 做                     |

**運算型態：Lambda 有三種，今天只講 Event**

| 型態            | 是什麼             | 最長時間            |
| --------------- | ------------------ | ------------------- |
| Event Functions | 事件來了才跑的函式 | 每次 15 分鐘        |
| Web Functions   | 常駐的網頁伺服器   | 每個請求 15 分鐘    |
| MicroVMs        | 每人專屬的隔離環境 | 每個 session 8 小時 |

**觸發：事件一來就跑，跑完就停**

- S3、API Gateway、SQS 等事件 → Lambda `handler` → 結果
- 超過 200 種 AWS 服務可以當觸發來源

**檢查點：用了 Lambda 之後，下列哪一項仍然要你自己做？**

- ✓ 撰寫 `handler` 程式
- ✗ 修補作業系統、規劃機器容量、決定機器數量來擴縮：這三項都歸 Lambda

> 一句話：Lambda 是函式服務，機器歸 AWS，你只管 handler。

## 二、函式基礎：入口、輸入輸出、記憶體

**三件事**

- handler 收兩個參數
- event 轉成 dict
- 記憶體決定 CPU

**Handler：Lambda 先找到的入口函式**

```python
def lambda_handler(event, context):   # event 是輸入，context 是執行資訊
    name = event['name']
    return 'Hi ' + name
```

- 設定值寫成「**檔名.函式名**」，例：檔名 `lambda_function` + 函式名 `lambda_handler` → `lambda_function.lambda_handler`
- 簽章**一定要有兩個參數**

**event：JSON 進來，Python 轉成對應型態**

| JSON   | Python       |
| ------ | ------------ |
| object | dict         |
| array  | list         |
| number | int 或 float |
| string | str          |

**回傳值：同步會回給呼叫端，非同步直接丟棄**

| 呼叫方式 | InvocationType    | 回傳值        | 有沒有人等結果 |
| -------- | ----------------- | ------------- | -------------- |
| 同步     | `RequestResponse` | JSON 回呼叫端 | 有             |
| 非同步   | `Event`           | 丟棄          | 沒有           |

**初始化：憑證自動給，設定從環境變數讀**

```python
s3 = boto3.client('s3')                    # 憑證由執行角色自動提供，不用寫 key
BUCKET = os.environ.get('BUCKET_NAME')     # 設定從環境變數讀（BUCKET_NAME：存檔的 S3 桶名）
def lambda_handler(event, context):
    ...
```

**記憶體：只有一個旋鈕，CPU 跟著它走**

- 可選範圍 128 MB（最小）到 10,240 MB（最大）
- 舉例：1,769 MB ≈ 1 vCPU；3,538 MB（×2）≈ 2 vCPU
- **CPU 不能單獨調，加記憶體就等於加 CPU**

**檢查點：Python handler 只宣告一個參數 `def lambda_handler(event)`，會怎樣？**

- ✓ Lambda 執行時報錯：簽章一定要有兩個參數
- ✗ `context` 自動省略：不會自動省略
- ✗ 自動改成非同步：呼叫方式跟簽章無關
- ✗ `event` 變空字典：`event` 內容不受簽章影響

> 一句話：Handler 是入口，兩個參數進，一個值出。

## 三、定價與限制：用量計費，單次 15 分鐘

**三件事**

- 記憶體乘秒數計費
- 單次 900 秒上限
- 套件有大小限制

**計費：記憶體 × 秒數 × 次數，沒人用就是零**

- 算力單位是 **GB-秒**；每月有免費額度，請求另外計費

**試算：官方範例一個月約 2.73 美元**（前提：每月 300 萬次、每次 120 毫秒、1,536 MB）

| 項目 | 算式                                           | 金額      |
| ---- | ---------------------------------------------- | --------- |
| 算力 | （54 萬 − 40 萬免費）GB-秒 × 0.0000166667 美元 | 2.33 美元 |
| 請求 | （300 萬 − 100 萬免費）次 × 0.2 美元／百萬次   | 0.40 美元 |
| 合計 |                                                | 2.73 美元 |

- 每月免費額度：100 萬次請求、40 萬 GB-秒（a09 也提過）

**執行限制：一般函式 15 分鐘是硬上限**

| 項目           | 上限              |
| -------------- | ----------------- |
| 單次執行       | 15 分鐘（900 秒） |
| 同步請求與回應 | 各 6 MB           |
| 記憶體         | 128 到 10,240 MB  |
| 環境變數合計   | 4 KB              |

**套件：壓縮 50 MB、解壓 250 MB，更大走容器映像**

| 項目                   | 上限   |
| ---------------------- | ------ |
| zip 上傳（API 或 SDK） | 50 MB  |
| 解壓後（含 Layer）     | 250 MB |
| 容器映像               | 10 GB  |

**檢查點：配置 2 GB、每次 500 ms、一個月 100 萬次，共用多少 GB-秒（不扣免費額度）？**

- ✓ 100 萬：2 GB × 0.5 秒 × 100 萬次
- ✗ 50 萬：漏乘了記憶體
- ✗ 200 萬：把 500 ms 當成 1 秒
- ✗ 要知道區域才算得出來：區域只影響單價

> 一句話：Lambda 按用量計費，單次不超過 15 分鐘；記憶體乘秒數乘次數，沒人用就是零。

## 四、呼叫模型：差在誰負責重試

**三件事**

- 同步：呼叫端重試
- 非同步：Lambda 重試
- 輪詢：Lambda 去拉

**三種呼叫**

| 呼叫   | 怎麼運作                          | 常見來源                       | 出錯誰負責       |
| ------ | --------------------------------- | ------------------------------ | ---------------- |
| 同步   | 呼叫端等結果（`RequestResponse`） | API Gateway                    | 呼叫端自己重試   |
| 非同步 | 先進內部佇列就回應（`Event`）     | S3、SNS、EventBridge           | Lambda 自動重試  |
| 輪詢   | poller 去拉資料，一批一批叫函式   | SQS、Kinesis、DynamoDB Streams | Lambda 的 poller |

- 輪詢靠 **event source mapping**：每筆至少處理一次
- 三種的差別只有一個問題：**出錯了誰負責**

**檢查點：API Gateway 同步呼叫 Lambda，函式執行失敗，誰決定要不要重試？**

- ✓ 呼叫端自己決定：錯誤回到呼叫端
- ✗ Lambda 自動重試兩次：自動重試屬非同步
- ✗ 事件進死信佇列：死信佇列屬非同步失敗
- ✗ poller 重新拉取：poller 屬輪詢

> 一句話：三種呼叫，三種重試責任，問誰在等結果。同步看呼叫端，非同步看 Lambda，輪詢由 Lambda 去拉。

## 五、Layer 與別名：套件共用，流量慢切

**三件事**

- Layer 共用套件
- 版本發布後不可改
- 別名按權重分流量

**Layer：共用套件抽出來，多支函式一起掛**

| 項目       | 規則                    |
| ---------- | ----------------------- |
| 每個函式   | 最多 5 層               |
| 掛載位置   | 解壓到執行環境的 `/opt` |
| Layer 版本 | 不可變，掛時指定版號    |
| 大小       | 連 Layer 解壓後 250 MB  |

**版本與別名：套件、程式、流量三樣分開管**

| 概念      | 說明                                                           |
| --------- | -------------------------------------------------------------- |
| `$LATEST` | 可修改的草稿                                                   |
| 版本 1、2 | 發布才有編號，**已發布的版本不能再改**                         |
| 別名      | 指到哪版就走哪版，還能切權重；**一個別名最多指兩個已發布版本** |

**金絲雀部署：先放一成流量，有問題指回舊版**

1. 發布版本 2
2. 別名 `prod` 分 10% 給版本 2（90% 仍走版本 1）
3. 看錯誤率
4. 全切或回滾

- 流量小的時候，實際比例會和設定值有落差

**檢查點：一個 Lambda 別名最多可以同時指向幾個版本做權重分流？**

- ✓ 2 個，而且都必須是已發布的
- ✗ 1 個：太少，無法分流量
- ✗ 5 個：那是 Layer 的上限
- ✗ 沒有限制：別名有明確上限

> 一句話：Layer、版本、別名管的是套件、程式、流量。三樣東西分開管，改版才有退路。

## 六、冷啟動：初始化只做一次，不夠再花錢預熱

**三件事**

- Init 只跑一次
- client 放 handler 外面
- 預配並行要付費

**生命週期：建環境、Init、handler 三段**

| 啟動   | 經過的階段                      |
| ------ | ------------------------------- |
| 冷啟動 | 建環境 → Init → handler         |
| 暖啟動 | 略過建環境與 Init，只跑 handler |

**程式位置：Init 寫在 handler 外面，暖啟動才能重用**

| client 放哪 | 結果           |
| ----------- | -------------- |
| handler 裡  | 每次呼叫都重建 |
| handler 外  | 暖啟動直接重用 |

**冷啟動代價：不常發生，但 Init 也計費**

- 不到 1% 的呼叫會遇到冷啟動
- 冷啟動多出的時間：100 ms 到 1 s 以上
- 另外：**Init 的時間也要計費**

**兩種並行：預配並行會額外收費**

| 項目 | 預配並行 provisioned | 預留並行 reserved |
| ---- | -------------------- | ----------------- |
| 作用 | 預先初始化環境       | 保留名額與上限    |
| 收費 | **額外收費**         | 不另外收費        |
| 目的 | 減少冷啟動           | 保證有名額可用    |

**取捨：先用便宜的招，不夠再用錢買**

| 做法               | 費用   |
| ------------------ | ------ |
| client 放外面      | 免費   |
| 只載入用得到的套件 | 免費   |
| 預配並行           | 要付費 |

**檢查點：預配並行和預留並行，哪一個會額外收費？**

- ✓ 預配並行額外收費
- ✗ 預留並行：只是保留名額，官方寫不收費

> 一句話：冷啟動，先省後花，預熱要付錢。client 放外面，只載入需要的套件，不夠再買預配並行。

## 七、非同步失敗：重試用完事件就丟，先留一份

**三件事**

- 預設重試 2 次
- 事件最長留 6 小時
- 死信佇列與失敗目的地

**重試流程**

- 事件 → 執行 → 失敗 → 重試 2 次 → 仍失敗 → **丟棄**
- **丟棄時沒有任何通知**

**重試時間：間隔 1 分鐘與 2 分鐘，事件最長留 6 小時**

| 次序    | 時間     |
| ------- | -------- |
| 第 1 次 | 最初執行 |
| 第 2 次 | 1 分鐘後 |
| 第 3 次 | 2 分鐘後 |

- 重試次數可設 0 到 2；事件最長保留時間可設，上限 6 小時

**留底：失敗目的地比死信佇列資訊多**

| 項目 | 死信佇列 DLQ | 失敗目的地 on-failure destination |
| ---- | ------------ | --------------------------------- |
| 可接 | SQS 或 SNS   | SQS、SNS、S3、Lambda、EventBridge |
| 內容 | 只有事件本身 | 事件加回應與錯誤細節              |

**設定注意**

- 執行角色要有發送權限
- SQS／SNS 目的地要用標準佇列或主題，**FIFO 不支援**

**檢查點：Lambda 非同步呼叫預設會自動重試幾次（不含最初那一次）？**

- ✓ 2 次：間隔 1 分鐘與 2 分鐘
- ✗ 0 次：不是預設，是可設範圍 0 到 2 的一端
- ✗ 1 次：是 2 次
- ✗ 3 次：這是含最初那次的總執行次數

> 一句話：非同步沒人等結果，失敗要事先留底。死信佇列或失敗目的地，二者至少設一個。

## 八、AI 連結：agent 放不進，工具放得進

**三件事**

- agent 常跑數小時
- Lambda 短又無狀態
- 長任務換執行環境

**15 分鐘：agent 一次任務放不進 Lambda**

- 例：查五份文件、呼叫三個工具、等人工核准 — 加起來可能跑數小時，超出 15 分鐘上限的部分放不進（示意，不照比例）

**等人的時間：Lambda 還在算錢，狀態也留不住**

- 等人工核准時，Lambda 計時中，環境被收掉，狀態消失

**工具：Lambda 最適合當 agent 的手腳**

| 角色   | 做什麼                                |
| ------ | ------------------------------------- |
| Agent  | 決定下一步                            |
| Lambda | 查訂單、發通知 — 短、無狀態、按次計費 |

**長任務選項：Lambda 家族已有三種延長法**

| 選項              | 是什麼                   | 最長時間          |
| ----------------- | ------------------------ | ----------------- |
| Durable functions | 可暫停、等待後接續的函式 | 整段流程一年      |
| Managed Instances | 跑在你帳號 EC2 上的函式  | 非同步 90 分鐘    |
| MicroVMs          | 每人專屬的隔離環境       | 每 session 8 小時 |

**檢查點：要查五份文件、等人工核准的 agent，為什麼不適合直接放進 Lambda Event Function？**

- ✓ 單次最長 15 分鐘，等待也計費
- ✗ Lambda 不能呼叫其他服務、不支援 Python、一定要放進 VPC：三個都不成立，VPC 與時間上限無關

> 一句話：Lambda 是 agent 的手腳，短工具放這裡；長任務看 durable functions、Managed Instances、託管 agent 環境。

## Takeaway

**Serverless 與 Lambda：限制決定它的角色**

1. 機器歸 AWS，你只管 handler
2. 記憶體與 15 分鐘是邊界，CPU 跟著記憶體走
3. 三種呼叫、三種重試責任；非同步失敗要事先留底
4. agent 放不進、工具放得進
