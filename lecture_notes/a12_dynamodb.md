## 一、單表設計：先列查詢，再設計鍵

**三件事**

- 先列出系統要回答的查詢
- 用鍵把同一個查詢要的資料放在一起
- 單表＝多種資料放同一張表，靠鍵分開；官方建議表愈少愈好

**單表長相：同一個 PK 的資料排在一起**

| 分區鍵 PK | 排序鍵 SK      | 屬性（信箱或狀態） |
| --------- | -------------- | ------------------ |
| USER#1    | PROFILE        | a@b.com            |
| USER#1    | ORDER#10-18#18 | SHIPPED            |
| USER#1    | ORDER#10-19#19 | PENDING            |

- PK 找到那一堆，SK 排好順序
- `PROFILE` 是使用者資料，`ORDER#…` 是訂單

**Query：最近十筆訂單，一次搞定**

```python
# 用 PK 鎖定使用者，SK 以 ORDER# 開頭，ScanIndexForward=False 由新到舊
# Limit=10 是「最多評估十項」
query(
  KeyConditionExpression=Key("PK").eq("USER#1")
    & Key("SK").begins_with("ORDER#"),
  ScanIndexForward=False, Limit=10)
```

**GSI（全域次要索引）：換一把鑰匙，查另一種問題**

| 項目 | 基表                  | GSI1            |
| ---- | --------------------- | --------------- |
| PK   | `USER#<id>`           | `STATUS#<狀態>` |
| SK   | `ORDER#<日期>#<編號>` | `<日期>`        |

- `< >` 換成實際值
- **只有帶 `GSI1PK` 的項目才會進索引**

**CCP 考點**

- 鍵值（key-value）資料庫、大規模下次毫秒（低於 1 毫秒）延遲 → **DynamoDB**；Aurora 是關聯式、DocumentDB 是文件型、Neptune 是圖形資料庫（題庫 CLF-C02 2026Q3 第 0066 題）

> 一句話：先列查詢，再設計鍵：同一個問題的資料放一起。PK 找到那一堆，SK 排好順序。

## 二、容量模式：不確定就 on-demand

**三件事**

- on-demand：按請求付費，官方預設且推薦
- provisioned：先訂每秒容量，按小時付費
- 兩種模式可以切換，次數有限制

**怎麼選：流量猜得準才用 Provisioned**

| 流量穩定、可預測？ | 選擇        | 補充                       |
| ------------------ | ----------- | -------------------------- |
| 是                 | Provisioned | 自動調整容量，目標用掉 70% |
| 否                 | On-demand   | 按請求付費                 |

- **節流**：請求超過容量被拒絕，要稍後重試

**讀的兩種：強一致與最終一致**

| 項目 | 強一致讀               | 最終一致讀                     |
| ---- | ---------------------- | ------------------------------ |
| 結果 | 保證讀到最新寫入的資料 | 可能讀到稍舊的資料，之後會追上 |
| 成本 | 基準（1 倍）           | 強一致的一半                   |

- **最終一致讀是預設；索引（GSI）只能最終一致讀**

**容量單位：4 KB 讀、1 KB 寫**

| 要做的事   | 單位                | 1 個單位可以做到          |
| ---------- | ------------------- | ------------------------- |
| 強一致讀   | RCU（讀取容量單位） | 每秒讀 1 筆，每筆 4 KB 內 |
| 最終一致讀 | RCU                 | 每秒讀 2 筆，每筆 4 KB 內 |
| 寫入       | WCU（寫入容量單位） | 每秒寫 1 筆，每筆 1 KB 內 |

- 講義範例：3 KB 不滿 4 KB 算 1 RCU，×80＝80 RCU（×80 的前提投影片沒寫，待查證）

**CCP 考點**

- 全受管、輸送量容量可自動擴展的 NoSQL 資料庫 → **DynamoDB**；Redshift 是資料倉儲，Aurora、RDS 是關聯式（題庫第 0055 題）

> 一句話：不確定就 on-demand，穩定可預測再 provisioned。強一致讀 4 KB 一個 RCU，寫入 1 KB 一個 WCU。

## 三、變更串流：表自己寫日記，別人來讀

**三件事**

- 新增、修改、刪除，各記一筆
- 記錄最多保存 24 小時
- 記錄只出現一次，同項目依序；處理端仍可能收到重複

**資料流：寫入表，記錄進 Stream**

- DynamoDB 表（訂單狀態改變）→ Stream（24 小時日誌）→ Lambda（例：寄出貨通知）
- Stream 非同步產生，**不影響表的效能**

**StreamViewType：記錄裡放多少內容**

| 類型                 | 內容             |
| -------------------- | ---------------- |
| `KEYS_ONLY`          | 只有被改項目的鍵 |
| `NEW_IMAGE`          | 改後的整筆項目   |
| `OLD_IMAGE`          | 改前的整筆項目   |
| `NEW_AND_OLD_IMAGES` | 改前與改後都有   |

- **不能改**：要換就關掉再另開新 Stream
- 要比對改前改後，選 `NEW_AND_OLD_IMAGES`

**CCP 考點**

- 共同責任模型下，DynamoDB 的**資料表存取控制（IAM policy）是客戶的責任**；實體安全、修補更新、靜態資料加密的流程由 AWS 負責（題庫第 0005 題）
- 講義註記：題庫沒有串流題，這題屬責任分工複習

> 一句話：寫入表就有日誌，Lambda 讀日誌做後續。

## 四、記憶體快取層：重複讀很多，才值得放 DAX

**三件事**

- DAX 是 DynamoDB 專用的記憶體快取
- 最終一致讀從個位數毫秒降到微秒（差約 1000 倍）
- 強一致讀、寫入密集不適合

**讀取路徑：命中直接回，未命中才問 DynamoDB**

| 情況   | 流程                            |
| ------ | ------------------------------- |
| 命中   | DAX 直接回，不經過 DynamoDB     |
| 未命中 | DAX 轉問 DynamoDB，存進快取再回 |

- 應用程式用 DAX client 連 DAX 叢集
- TTL 5 分鐘；LRU＝淘汰最久沒用的；write-through＝兩邊都寫

**什麼時候用：讀得多、重複讀**

| 適合                 | 不適合     |
| -------------------- | ---------- |
| 熱門商品被大量重複讀 | 要強一致讀 |
| 讀多，想少買讀取容量 | 寫入密集   |
|                      | 很少重複讀 |

- 官方：**快取命中率超過 90%** 時效果最好

**CCP 考點**

- 每秒數百萬筆查詢、隨需求擴展的資料儲存 → **DynamoDB**；ElastiCache 是記憶體快取、用來減輕資料庫負載，**不是主要的持久儲存**；Cloud9 是開發環境、Neptune 是圖形資料庫（題庫第 0518 題）

> 一句話：重複讀多、能接受最終一致，才加 DAX。命中率愈高愈划算。快取不是正本。

## 五、實作：五個查詢需求，設計一張單表

這是紙上設計作業，不用開資源，沒有費用，也不需要清理。

**五個查詢需求**

| 編號 | 需求                                     |
| ---- | ---------------------------------------- |
| P1   | 用 Email 找到使用者                      |
| P2   | 取某使用者的基本資料                     |
| P3   | 取某使用者最近十筆訂單                   |
| P4   | 取某筆訂單與它的所有品項                 |
| P5   | 列出某狀態（例如待出貨）的訂單，由新到舊 |

**必做：六步**

1. **抄下 P1 到 P5**：每個一行
2. **畫項目表**：每列一個項目，寫 PK、SK、屬性；至少 8 列
3. **寫鍵條件**：PK 等於什麼，SK 用什麼條件
4. **需要時加 GSI**：標明該 GSI 自己的 PK、SK
5. **寫一句理由**：為什麼不用 Scan（Scan＝讀整張表）
6. **自我檢查**：五個查詢都不需要 Scan

**怎麼交：一份文件，三樣東西**

1. 項目表：PK、SK、屬性
2. 查詢對照：P1 到 P5 各用什麼鍵
3. 每個查詢一句理由

- 手寫拍照或電子檔
- 交給誰與期限：講義寫「尚未決定，由講師上課當天公布；自學者先自己檢查即可」
- 本作業為講師自擬題目

## Takeaway

1. 先列查詢，再設計鍵；PK 找到那一堆，SK 排好順序，要換查法就加 GSI
2. 不確定就 on-demand；強一致讀 4 KB 一個 RCU，寫入 1 KB 一個 WCU
3. Streams 保存 24 小時變更記錄，要比對改前改後選 `NEW_AND_OLD_IMAGES`
4. DAX 只在重複讀多、接受最終一致時才划算；快取不是正本
