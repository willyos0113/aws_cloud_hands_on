## 一、單點失敗與健康檢查：機器活著不代表服務活著

- 先定義六個詞，後面反覆用：**單點失敗**（single point of failure，這個元件一掛整個服務就掛）、**負載平衡器**（load balancer，站在使用者跟機器中間分流量）、**健康檢查**（health check，定期發請求看回不回、回什麼）、**目標群組**（target group，一組機器加共用的 health check 設定）、**Auto Scaling 群組**（ASG，把一組機器當一個單位管，讓實際台數等於期望台數）、**擴展策略**（scaling policy，自動改「現在要幾台」這個數字的規則）
- 掛法分三種，只有第一台機器算單點失敗；講師經驗裡最常見的是第三種：

| 掛法             | 例子                              | 誰看得到                                              |
| ---------------- | --------------------------------- | ----------------------------------------------------- |
| AWS 那一側壞了   | 主機硬體、電力、網路連不到        | EC2 的 system status check                            |
| 機器裡面壞了     | 作業系統起不來、網路設定錯        | EC2 的 instance status check                          |
| 服務死了機器沒死 | process 還在，但回 500 或卡住不回 | system 跟 instance 都看不到，只有 health check 抓得到 |

- **兩層健康檢查各看各的**：第一層 EC2 status check（AWS 自動做、免費）只看「這個盒子還在不在」；第二層負載平衡器的 health check（自己設定）才是真的打服務——預設每 30 秒 GET 一次指定路徑，回 200 算過，逾時或非 200 算失敗；連續失敗到門檻就踢出輪替（不再送流量，機器還在原地），連續成功到門檻再放回來；全部目標都不健康時會 **fail open**，流量照送給所有機器，避免整站空轉
- 常見誤解：以為負載平衡器判定不健康那台機器就會被自動換掉。實際上**踢出輪替只是不再送流量**，機器還在；**Auto Scaling 預設只看 EC2 的 status check**，要在群組上另外打開 ELB health check，它才會去換掉負載平衡器判定不健康的機器
- 負載平衡器做的三件事：**單一入口**（使用者只認一個 DNS 名稱，不用每加一台就改 DNS）、**分流到多個 AZ**（每個啟用的 AZ 有一個節點，一個 AZ 掛不會整站掛）、**只送給健康的**（靠 health check 判斷）；它本身是 AWS 管的跨 AZ 服務，不會變成新的單點

## 二、ALB 與 NLB：兩種負載平衡器

- 一句話分野：**ALB 看信的內容，NLB 只看信封**；高併發、要固定 IP、非 HTTP 才選 NLB，其他情況預設用 ALB
- **ALB**（Application Load Balancer）在 OSI 第七層（應用層）工作，看得懂 HTTP；四個零件：**監聽器**（listener，聽某個埠，例如 HTTPS 443）→ 底下掛幾條**規則**（優先順序＋條件＋動作，數字小的先比，比中就停，一定有一條預設規則）→ 每條規則 forward 到一個**目標群組**（target group，各自有自己的 health check）→ 群組裡是實際的**目標**
- 規則＝條件加動作，左右自由組合（左右不是同列配對，一條規則最多五個比對值）：

| 條件（看什麼）           | 例子             | 動作（做什麼）                     |
| ------------------------ | ---------------- | ---------------------------------- |
| host-header 主機名       | api.example.com  | forward：轉給某個目標群組          |
| path-pattern 路徑        | /admin/\*        | redirect：轉址，例如 http 轉 https |
| http-header 任一 header  | X-Client: mobile | fixed-response：直接回一段文字     |
| http-request-method 方法 | POST             | authenticate：先驗身分再轉         |
| query-string 查詢字串    | version=beta     | —                                  |

- 專題常用兩條規則：`/api/*` 轉給 agent 後端的目標群組、其他請求轉給前端那組機器；另外 80 埠的監聽器只放一條 redirect 到 443（前提是 443 已經建好 HTTPS 監聽器跟憑證），不用改程式就強制 HTTPS；規則寫在 ALB 的設定裡，不跟著任何一台機器，機器換了規則還在
- ALB 附送的不只分流：支援 HTTP/2 與 WebSocket（聊天介面可以走 WebSocket，但連線升級成 WebSocket 之後監聽器規則跟 WAF 不再套用）；Lambda 可以直接當目標（serverless 後端也能掛同一個 ALB）；前面可以掛 AWS WAF 擋 SQL 注入這類第七層攻擊；**閒置逾時**預設 60 秒（一條連線多久沒資料就切），LLM 串流會踩到這個坑
- **NLB**（Network Load Balancer）在 OSI 第四層（傳輸層）工作，只看 IP 跟埠、不拆內容，換來速度與固定 IP：

| 面向     | ALB                          | NLB                                          |
| -------- | ---------------------------- | -------------------------------------------- |
| 層級     | 第七層，拆開 HTTP 看內容     | 第四層，只看 IP 跟埠                         |
| 協定     | HTTP、HTTPS、WebSocket、gRPC | TCP、UDP、TLS、QUIC                          |
| 位址     | 只給 DNS 名稱，IP 會變       | 每個 AZ 一個固定 IP，對外型還可綁 Elastic IP |
| 分流依據 | 規則：主機名、路徑、header   | flow hash：同一條連線固定送同一台            |
| 效能     | —                            | 每秒百萬級請求，延遲比 ALB 低（講師經驗）    |

- 三個訊號詞任一出現就選 NLB：**極高併發、極低延遲、每秒百萬請求**（第四層不拆內容）；**客戶要白名單、每個 AZ 要固定 IP**（ALB 只給 DNS 名稱）；**非 HTTP**，例如遊戲、IoT、自訂 TCP 協定（ALB 只懂 HTTP）；看到網址分流、轉址、WAF、WebSocket 這類第七層需求才選 ALB。兩種也可以疊著用：NLB 在前給固定 IP，ALB 當它的目標繼續分流
- 跨 Region 分流不能只靠 ALB／NLB（兩者都只在一個 Region 裡分流）：**Global Accelerator** 在邊緣給兩個全球固定 IP，把使用者導到最近或最健康的 Region；**Route 53** 用 DNS 回覆把使用者導到別的 Region；NLB 解的只是一個 Region 內的固定 IP，專題的 agent API 是 HTTP，多半用不到 NLB

## 三、Auto Scaling：把「應該有幾台」寫成數字交給服務盯

- **ASG 只做一件事**：讓實際台數等於期望台數。**Launch Template**（啟動模板）先寫好 AMI、機型、Security Group、User Data、IAM Role，開每一台都照它；群組上設 **min / desired / max** 三個數字：min 是台數天花板的下限（再閒也不低於）、max 是天花板（帳單大致跟著它走）、desired 是現在要幾台（擴展策略改的就是它）——desired 永遠被夾在 min 到 max 之間
- **ASG 不修機器，它換機器**：監控（預設用 EC2 status check 判斷，打開 ELB health check 後也聽負載平衡器的）→ 判定（連續失敗就標成 Unhealthy，新機器有一段 **grace period** 寬限期不把檢查失敗當換機理由）→ 終止（有 connection draining 就先等進行中的請求做完）→ 補位（實際台數低於 desired，照模板在機器最少的 AZ 補一台）；少的原因不管是機器掛了、你手動終止、還是整個 AZ 不見，它都照補
- 三件事 ASG 不會替你做：**打開 ELB health check**（預設只看 EC2 status check，程式死了它不知道）、**選兩個 AZ 的子網路**（AZ 由你選的子網路決定，只選一個 AZ 它就只開在那裡）、**機器要無狀態**（檔案放 S3 或 EFS、session 放資料庫或快取，因為機器隨時會被換掉）——機器是牛，不是寵物
- On-Demand 保底，Spot 接尖峰（前提是機器無狀態；列的機型越多，Spot 越不容易缺貨）：On-Demand 基底設一個固定台數當保底，超過基底的機器再按比例分 On-Demand／Spot，列幾個能接受的機型讓 Spot 缺貨時能換一種；Spot 被收回時 ASG 當成一台掛了照樣補
- 四種擴展策略，能反應現在也能提前動手：

| 策略                     | 白話                             | 誰觸發                   | 適合                 |
| ------------------------ | -------------------------------- | ------------------------ | -------------------- |
| 目標追蹤 target tracking | 像恆溫器：每台 CPU 維持 50%      | CloudWatch 指標偏離目標  | 大多數情況的預設     |
| 步進與簡單 step / simple | CPU 過 60 加 2 台，過 80 加 4 台 | 你設的 CloudWatch 警報   | 要精細控制每一階     |
| 排程 scheduled           | 平日 08:00 改成 4、20:00 改回 2  | 時間，cron 語法          | 已知的尖峰           |
| 預測 predictive          | 每天九點都衝高，八點五十先開     | 機器學習對歷史流量的預測 | 有週期又開機慢的服務 |

- 同一天三種策略各管一段：排程先在尖峰前開好機器、預測提前熱身、目標追蹤整天盯著當下；每次加機器後有 **warmup**（暖機期，新機器這段時間的指標不算進群組平均）與 **cooldown**（冷卻期，簡單擴展做完一次動作先等一下再做下一步，預設都是 300 秒），避免忽加忽減。先問尖峰能不能預知：預知不到用目標追蹤（不用自己算要加幾台）、已知的尖峰用排程（注意 cron 沒指定時區就是 UTC，台灣 06:30 是 UTC 前一天 22:30）、有週期又開機慢用預測（需要歷史資料，新上線、活動促銷這種一次性尖峰它看不出來）；題庫說的**彈性（Elasticity）**，就是 desired 會自己動
- 選指標的規則：**要反映每台有多忙，不能用總量**（台數加倍指標要跟著掉一半，例如平均 CPU、每台請求數；負載平衡器的總請求數不會因為多開機器變少，不能用）；**解析度一分鐘以內**（五分鐘一筆反應太慢）；**排隊型工作看每台積壓量**（佇列長度除以在線台數，例如 SQS）。CPU 只有真的是瓶頸時才準，忙在等 GPU、等下游時 CPU 可能只有 20%

## 四、LLM 應用的擴展：前面的做法套上去，三個地方會壞

- 一般 Web API 一個請求幾十毫秒回完，瓶頸在 CPU；LLM 服務一個請求要幾秒到幾十秒，一路吐字，瓶頸在 GPU 記憶體與同時處理的請求數。前面幾段的做法是為「幾十毫秒回一個 JSON」的網站設計的，套到 LLM 服務會壞在**指標、逾時、健康檢查**三處，而且三處都不會報錯，只會慢慢爛：

| 面向           | 一般 Web API         | LLM 推論服務                   |
| -------------- | -------------------- | ------------------------------ |
| 一個請求多久   | 幾十毫秒             | 幾秒到幾十秒                   |
| 瓶頸在哪       | CPU                  | GPU 記憶體、同時處理的請求數   |
| 擴展指標       | 平均 CPU、每台請求數 | 每台同時請求數、每台排隊數     |
| 新機器多久能用 | 秒級                 | 分鐘級，要載幾十 GB 權重       |
| 健康檢查       | `/health` 回 200     | 跑極小的推論，或確認模型已載入 |

- **指標**：自架 LLM 推論的忙多半在 GPU 跟排隊，不是 CPU（機器已經滿載，CPU 可能只有 20%，用平均 CPU 做目標追蹤策略會以為很閒，擴不起來）——改看「每台同時處理幾個請求」或「每台排隊幾個」（SQS 那套），這兩個都是自訂指標
- **逾時**：閒置逾時計的是「多久沒資料」，不是總共多久。**串流**（streaming）讓模型每生成一段就先送出，不等整段答完——token 持續在流就不會被切；會被切的是超過 60 秒沒有 byte 的空窗（例如第一個 token 等太久、或非串流一次回）。官方解法兩條：每個閒置逾時週期內至少送一個 byte 佔線，或直接把閒置逾時調大；另外服務自己的 keep-alive 逾時要比 ALB 的長，不然服務先關連線，ALB 又把下一個請求送進來，使用者會拿到 502。Bedrock 的串流 API 是 ConverseStream：收到 delta 就往前送，連線一直有資料
- **健康檢查**：`/health` 回 200 只證明 web 框架活著，不代表模型載好——模型沒載好、GPU 記憶體爆了，它照樣回 200。健康檢查要真的問一句：跑一個極小的推論，或至少確認模型已載入、下游可達
- 用 Bedrock 時，模型那一側的擴展是 AWS 的事，不用管 GPU；你只管自己的 agent 服務，架構還是 ALB 加 ASG，但四個設定要跟著改：閒置逾時從預設 60 秒調到幾分鐘、回應方式從非串流一次回改成一律串流、健康檢查從固定回 200 改成確認能連到 Bedrock、擴展指標從平均 CPU 改成每台同時請求數
- 金句：**LLM 服務是另一種形狀的服務——看併發不看 CPU、連線要撐得住、健康檢查要真的問一句**

## 一、核心實作：把常掛的單機改成不會掛

（分層評分：必做 70% / 進階 20% / 加分 10%）
三層都用主控台、零程式碼；講師給一支會自己崩的程式，一行都不改：

1. 必做一：建兩個 Security Group（`alb-sg` 開 80 對所有人，`app-sg` 的 8080 只放行來源 `alb-sg`），機器只收從 ALB 來的流量
2. 必做二：建 Launch Template（AMI、機型、`app-sg`、User Data 貼講師給的網址）
3. 必做三：先建目標群組（health check path 改 `/health`）再建 ALB，兩個 AZ 各選一個子網路
4. 必做四：建 ASG 指向這個目標群組，**勾 Elastic Load Balancing health checks**（grace period 60），min 2 / desired 2 / max 4——這一格是整堂課的考點
5. 必做五：瀏覽器打 ALB 的 DNS name 一直重新整理；終止一台機器記錄補齊要多久；什麼都不做等程式自己崩，記錄從 unhealthy 到被換掉要多久
6. 進階：把 ASG 的「Elastic Load Balancing health checks」取消勾選，等一台程式崩掉，觀察目標群組標 unhealthy 但 ASG 不換機——兩層健康檢查各看各的，要勾那一格 ASG 才知道服務死了
7. 加分：加一條 target tracking（指標 ALB request count per target，目標值 30），拿掉記錄迴圈裡的 sleep 狂打幾分鐘，看 desired 從 2 變 3 或 4

- 繳交：三張截圖（ha-tg 兩台 healthy、手動終止時的記錄加 ASG Activity、程式崩後的 Activity，各 15%／15%／12.5%／12.5%）+ 三行文字（終止到補齊幾分幾秒、崩潰到換掉幾分幾秒、進階那段看到什麼，沒做就寫「沒做」）+ 做了加分的附 scale out 那一筆 Activity
- 驗收重點：進階要寫出「目標群組 unhealthy 但 ASG 不換機」才算對；加分只要 desired 有上升就給分，縮回不強求

## 二、回家作業（略，參考用）

每份都拿自己的期末專題來寫：

1. **單點失敗與健康檢查**：替專題的 API 寫 `/health` 規格（5–8 行），加一行寫哪種故障它抓不到
2. **ALB 第七層路由**：一張 ALB 規則表，至少三條含預設，加一行寫 80 埠怎麼處理
3. **NLB 第四層場景**：替專題裡三個服務各選 ALB 或 NLB，各寫一行理由
4. **ASG 基礎**：專題 agent API 的 ASG 規格（min/max/desired、AZ、health check），8–10 行
5. **擴展策略**：一條目標追蹤策略，寫指標、目標值、理由、warmup，共五行
6. **LLM 應用的擴展**：用「指標、逾時、健康檢查」三個會壞的地方檢查上一份作業，原本／問題／改成三列三欄
