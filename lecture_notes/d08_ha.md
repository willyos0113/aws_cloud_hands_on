# d08 - 高可用與自動擴展：不怕機器掛、負載平衡、機器隨時換

[內容]

## 一、機器活著，不代表服務活著

- 六個詞先記起來：**單點失敗**（一個元件掛整站掛）、**負載平衡器**（站在使用者跟機器中間分流量）、**健康檢查**（定期問「你活著嗎」、回不回、回什麼）、**目標群組**（一組機器加共用的健檢設定）、**Auto Scaling 群組**（ASG，把一組機器當一個單位管、實際台數 = 期望台數）、**擴展策略**（自動改「現在要幾台」這個數字的規則）

- **掛的方式有三種，只有第一台算單點失敗**：AWS 那一側壞（硬體、電力、網路）、機器裡面壞（作業系統、設定）、服務死了機器沒死（process 還跑但回 500 或卡住）

- **兩層健康檢查各看各的**：EC2 status check（AWS 自動、免費）看「盒子還在不在」；負載平衡器的 health check（自己設定）才打服務——預設每 30 秒 GET 一次指定路徑，回 200 算過，失敗連續到門檻就踢出輪替（不再送流量、機器還在）

- 常見誤解：以為不健康的機器會被自動換掉；實際上 ASG 預設只看 EC2 status check，要打開 **ELB health check** 它才會去換掉 health check 判定不健康的機器

- 負載平衡器做三件事：**單一入口**（使用者只認一個 DNS）、**分流到多個 AZ**（一個 AZ 掛不會整站掛）、**只送給健康的**（靠 health check 判斷）；它本身是 AWS 管的跨 AZ 服務，不會變成新的單點失敗

## 二、ALB 看信的內容，NLB 只看信封

- **一句話分野**：ALB 看信的內容（拆開 HTTP）、NLB 只看信封（IP 跟埠）；高併發、要固定 IP、非 HTTP 才選 NLB，其他預設用 ALB

- **ALB**（第七層、應用層）結構是監聽器 → 規則 → 目標群組 → 目標；規則可以按主機名、路徑、header、方法、查詢字串來分流；專題常用兩條規則：`/api/*` 轉給 agent 後端、其他轉給前端；80 埠監聽器放一條 redirect 到 443（強制 HTTPS、程式碼零改動）

- ALB 支援 HTTP/2、WebSocket、Lambda 當目標；**閒置逾時預設 60 秒**（LLM 串流會踩坑、需要改大或改成串流）；前面可掛 AWS WAF；規則寫在 ALB，機器換了規則還在

- **NLB**（第四層、傳輸層）只看 IP 跟埠、不拆內容，換來速度與固定 IP；每個 AZ 一個固定 IP、對外型還可綁 Elastic IP；分流依據是 flow hash（同一條連線固定送同一台）；效能百萬級請求、延遲比 ALB 低

| 面向     | ALB                    | NLB                       |
| -------- | ---------------------- | ------------------------- |
| 層級     | 第七層、拆 HTTP        | 第四層、只看 IP 跟埠      |
| 協定     | HTTP、HTTPS、WS、gRPC  | TCP、UDP、TLS、QUIC       |
| 位址     | 只給 DNS、IP 會變      | 每 AZ 固定 IP             |
| 分流依據 | 規則：主機名、路徑等   | flow hash、同連線同目標   |
| 效能     | —                      | 百萬級請求、延遲更低      |

- 看到三個訊號詞任一就選 NLB：極高併發、極低延遲、每秒百萬請求；要固定 IP、白名單；非 HTTP（遊戲、IoT）；看到網址分流、轉址、WAF 才用 ALB

## 三、把「應該有幾台」寫成數字，交給服務盯

- **ASG 只做一件事**：讓實際台數等於期望台數；Launch Template 先寫好 AMI、機型、Security Group、User Data、IAM Role；群組上設 min / desired / max 三個數字：min 是天花板下限（再閒也不低於）、max 是天花板（帳單跟著走）、desired 是現在要幾台（擴展策略改的就是它）

- **ASG 不修機器，它換機器**：監控 → 判定不健康 → 終止 → 補位；預設用 EC2 status check，打開 ELB health check 後也聽負載平衡器的；新機器有 grace period 寬限期不把失敗當換機理由；有 connection draining 等進行中請求做完

- **三件事 ASG 不會替你做**：打開 ELB health check（預設只看 EC2）、選兩個 AZ 的子網路（AZ 由子網路決定）、機器要無狀態（檔案放 S3/EFS、session 放資料庫/快取、機器隨時被換掉）

- On-Demand 保底、Spot 接尖峰：On-Demand 基底設固定台數當保底、超過基底的機器按比例分 On-Demand/Spot；Spot 被收回時 ASG 當成掛了照樣補；列的機型越多 Spot 越不容易缺貨

- **四種擴展策略**：目標追蹤（像恆溫器、CPU 維持 50%、大多數情況預設）、步進簡單（CPU 過 60 加 2 台過 80 加 4、精細控制）、排程（平日 08:00 改 4 台、已知尖峰）、預測（每天九點衝高八點五十先開、有週期又開機慢）

- 同一天三種各管一段：排程先開好、預測提前熱身、目標追蹤整天盯著；每次加機器後有 warmup（新機器指標不算進平均）與 cooldown（等一下再做下一步、預設 300 秒）；選指標規則：**反映每台有多忙**（平均 CPU、每台請求數；不能用總量）；**解析度一分鐘內**；**排隊工作看每台積壓量**

## 四、前面的做法套在 LLM 服務，三個地方會壞

- 一般 Web API 幾十毫秒回完、瓶頸在 CPU；LLM 服務幾秒到幾十秒、瓶頸在 GPU 記憶體與同時處理數；前面的做法直接套會壞在**指標、逾時、健康檢查**，都不會報錯、只會慢慢爛

| 面向           | 一般 Web API      | LLM 推論服務            |
| -------------- | ----------------- | ----------------------- |
| 一個請求多久   | 幾十毫秒          | 幾秒到幾十秒            |
| 瓶頸在哪       | CPU               | GPU 記憶體、同時請求數  |
| 擴展指標       | 平均 CPU          | 每台同時請求數、排隊數  |
| 新機器多久能用 | 秒級              | 分鐘級、要載權重        |
| 健康檢查       | `/health` 回 200  | 跑極小推論或確認模型    |

- **指標**：自架 LLM 忙在 GPU、不是 CPU（滿載 CPU 可能只 20%）——改看「每台同時處理幾個請求」或「每台排隊幾個」（SQS 那套），這兩個都是自訂指標

- **逾時**：閒置逾時計的是「多久沒資料」、不是總共多久；串流讓模型生成一段就先送、token 持續流就不會被切；會被切的是超 60 秒沒 byte 的空窗；解法兩條：每個逾時週期內至少送一個 byte、或調大逾時；服務自己的 keep-alive 要比 ALB 的長

- **健康檢查**：`/health` 回 200 只證明 web 框架活著、不代表模型載好——改成跑極小推論或確認模型已載入

- **用 Bedrock 時**：模型擴展是 AWS 的事、不用管 GPU；你只管自己的 agent 服務，ALB 加 ASG，但四個設定要改：逾時從 60 秒調到幾分鐘、回應改串流、健康檢查確認連 Bedrock、擴展指標改每台同時請求數

- **金句**：LLM 服務是另一種形狀——看併發不看 CPU、連線要撐得住、健康檢查要真的問一句

## 一、驗收：手動終止一台，網站幾十秒內恢復

（分層評分：必做 70% / 進階 20% / 加分 10%）
全用主控台、零程式碼；講師給一支會自己崩的程式、一行都不改：

1. 必做一：機器只收從 ALB 來的流量
2. 必做二：開每一台都照 Launch Template
3. 必做三：先建目標群組、再建 ALB
4. 必做四：勾 ELB health check（整堂課的考點）
5. 必做五：終止一台再等它自己崩、ASG 補位
6. 進階：關掉 ELB health check，壞機器沒人換
7. 加分：加目標追蹤，desired 自己上升

- 繳交：三張截圖（目標群組兩台 healthy、終止時的 Activity、程式崩後的 Activity）+ 三行文字（終止到補齊幾分幾秒、崩潰到換掉幾分幾秒、進階看到什麼）+ 加分的 Activity
- 驗收重點：進階要寫「目標群組 unhealthy 但 ASG 不換機」；加分只要 desired 有上升就給分

## 二、回家作業：六份都是個人完成（略，參考用）

1. **健康檢查規格**：替專題 API 寫 `/health` 規格（5～8 行），加一行寫哪種故障它抓不到
2. **ALB 規則表**：至少三條含預設，加一行寫 80 埠怎麼處理
3. **NLB 選型**：替專題三個服務各選 ALB 或 NLB，各一行理由
4. **ASG 基礎**：Agent API 的 ASG 規格（min/max/desired、AZ、health check），8～10 行
5. **擴展策略**：一條目標追蹤，寫指標、目標值、理由、warmup，共五行
6. **LLM 應用調整**：用「指標、逾時、健康檢查」檢查專題，原本／問題／改成三列三欄
