## 一、讀懂型號命名

- 型號拆四段讀：家族 + 世代 + 屬性 + 大小，例：`c7g.xlarge` = c（運算優化）+ 7（第 7 代，越新越好）+ g（Graviton，AWS 自家 ARM，同效能便宜約兩成）+ xlarge（4 vCPU 8 GiB，每級翻倍）
- 家族字母對照：
  - **t/m**：一般用途（4GiB/vCPU），網站、API、開發機
  - **c**：運算優化（2GiB/vCPU），批次運算、影音轉檔
  - **r/x**：記憶體優化（8GiB+/vCPU），資料庫、記憶體快取
  - **i/d**：儲存優化，本機 NVMe 高 IOPS 資料庫
  - **p/g/inf/trn**：加速運算（GPU/AI 晶片），訓練、推論、繪圖
- 實務判斷：新專案優先選 Graviton（g 屬性，Python/Node 幾乎不用改）；世代越新越好；開發機用 t 家族最小台先測（t 是 burstable：平時給基準 CPU，累積點數後可短時間爆衝，持續高負載會被限速）
- 先開小台（如 micro 系列）測兩週，再用 **Compute Optimizer** 依實際使用率建議該換哪個家族/大小

## 二、定價模式（折扣用彈性換）

- **On-Demand**：無折扣，最貴，最有彈性
- **Reserved Instances(RI)**：綁約 1 或 3 年，折扣 3-7 成，中途不用也要付；Standard 要重買才能換家族，Convertible 可換；用不到可在 RI Marketplace 轉賣
- **Savings Plans**：承諾每小時花多少錢、不綁型號，折扣跟 RI 差不多，換家族照算，但不能轉賣；官方目前建議的預設選項
- **Spot**：用閒置容量，兩分鐘前通知收回，折扣最多九成，適合可中斷工作
- **Dedicated Hosts**：整台實體機，沒折扣最貴，只為帶舊軟體授權（綁實體核心數）上雲
- 易混淆三者：Dedicated Instances（只保證硬體不跟別人共用帳號）vs Dedicated Hosts（連實體核心位置都固定，授權綁核心數的軟體要它）vs Capacity Reservations（保證有機器但不打折，可跟 RI 疊用）
- 決策順序：能否被中斷 → 可以就 Spot；會不會用滿一年以上 → Savings Plans/RI；有無軟體授權綁實體核心 → Dedicated Hosts；都不是 → On-Demand 先用，量測完再換
- 建議：不要第一個月就承諾，先用 Cost Explorer 看穩定用量再買 RI/Savings Plans

## 三、Security Group（只會說可以，不會說不行）

- 三大特性：**執行個體層級**（一個 SG 可以同時掛在很多台 EC2 上，改一次全部生效）、**Stateful 有狀態**（允許進來的連線，回應自動放行，出站預設全開）、**只有 Allow**（沒寫就是拒絕，要擋特定 IP 得靠 NACL）
- 資料庫來源建議填「另一個 SG 的 ID」而非 IP 段：機器換 IP、Auto Scaling 擴新機器都不用改規則，因為規則描述的是角色（誰能連）而非位置（哪個 IP）
- 實務規則：0.0.0.0/0 只給 80/443（22 永遠不對全世界開）；一個角色一個 SG（網站/資料庫/跳板機分開，不要全塞在 default）；SG 是免費的，多開幾個沒成本
- 新建 SG 預設：入站什麼都不允許、出站全部允許

## 四、兩道門：SG vs NACL

|          | SG                         | NACL                                                   |
| -------- | -------------------------- | ------------------------------------------------------ |
| 綁定層級 | 執行個體                   | 子網路                                                 |
| 狀態     | Stateful（回應不用寫規則） | Stateless（進出都要寫規則）                            |
| 規則     | 只有 Allow                 | 有 Allow 也有 Deny，依編號小到大比對，第一條符合就套用 |
| 用途     | 單台機器的角色權限         | 整個子網路的邊界防護                                   |

- 兩者都只看 IP 跟埠，看不懂 HTTP 內容；擋 SQL injection 這類應用層（第七層）攻擊要用 **AWS WAF**

## 五、開機與進機器

- **UserData**（開機時才跑的 bash 腳本，第一行需要 `#!/bin/bash`，只在第一次啟動時跑一次，失敗不會擋開機，log 在 `/var/log/cloud-init-output.log`）vs **Golden AMI**（系統/軟體/設定先烤進映像，開機幾十秒就能服務）
- 搭配原則：重的東西烤進 AMI，會變的設定放 UserData
- UserData 三個坑：失敗不擋開機（機器會「開好但沒服務」，要看 cloud-init log）、不要把秘密寫進去（任何能讀機器 metadata 的程式都看得到明文）、長腳本要拆開處理
- **EC2 Image Builder**：AWS 的映像烤製服務，定義配方、排程重烤、自動測試，產出打版本標籤的 Golden AMI（概念類似 Docker image，但 AMI 包含整個作業系統）

## 六、無金鑰遠端維運（Session Manager）

- 傳統 SSH 逼你管四樣東西：私鑰 .pem（離職者留著/筆電丟了/貼進 repo 會出事）、跳板機（自己要補丁監控、多花一台錢）、22 port（每台機器多一個對外開口）、稽核（SSH 不會自動留下誰在幾點跑了什麼指令）
- **Session Manager**：機器自己主動連出去到 SSM 端點（走 HTTPS 出站），不用開任何入站埠、不用金鑰，你從 IAM 決定誰能連哪台 — 預設做法，ssh 跳板機已走入歷史
- 四個前提：機器裝有 SSM Agent（官方 AMI 多半預裝）、機器的 Role 掛 `AmazonSSMManagedInstanceCore`、機器能連到 SSM 端點（公網出口或 VPC endpoint）、你的身分有 `ssm:StartSession` 權限
- 三種連線方式比較：傳統 SSH+跳板（開 22、長期 .pem、無稽核）、**EC2 Instance Connect**（開 22 但來源可限 AWS IP 段、臨時 60 秒公鑰、有 API 記錄，是折衷選項）、Session Manager（不開 22、無金鑰、可記錄每個指令）
- 每次連線可設定記錄到 CloudWatch 或 S3（Session Manager Preferences，預設不開）

## 七、GPU 與 LLM（p 訓練、g 推論）

- p 家族＝訓練/大模型推論（如 p5 的 H100）；g 家族＝推論/繪圖/小模型微調（如 g5 的 A10G）；inf＝AWS 自家 Inferentia 推論晶片；trn＝AWS 自家 Trainium 訓練晶片
- 自架 GPU 使用率不到六成就輸託管模型：自架的錢花在「開著」，Bedrock 按 token 花在「用到」；沒呼叫就零元，尖峰 AWS 那邊擴，不用自己管驅動/CUDA/模型載入/監控/補丁
- 用量很滿很穩／自己微調的模型／資料不能離開 VPC 才適合自架，其他情況託管（Bedrock）划算
- Spot 適合跑批次向量化（embedding）：待處理文件放 S3 → Spot 的 g5/inf2 處理 → 每批完成就寫回 S3、進度記在 DynamoDB → 被收回就換新 Spot 機器接著跑，不用從頭開始，可省七到九成
- 金句：「GPU 機器是租一整台車，token 是搭計程車；一天坐兩趟就別買車」

## 八、EC2 狀態檢查的盲點

- EC2 Status check 只看機器活著（開機成功），看不出應用程式（如 nginx）死掉——服務死了，狀態檢查仍可能顯示 2/2 passed，「機器活著 ≠ 服務活著」
