# 資料庫 RDS、Aurora 與快取

---

## 一、資料庫交給 AWS 養，再多一台

**同一個 MySQL，責任線換了位置**

- EC2 自建：你管理系統、裝軟體、備份、故障切換、維護
- RDS 受管：AWS 代管 MySQL/PostgreSQL 等，你管應用層邏輯

**RDS 替你做掉三件事**

| 工作              | RDS 做法                           | 你要做的                 |
| ----------------- | ---------------------------------- | ------------------------ |
| 修補              | 排在每週維護時段自動套用           | 選離峰時段               |
| 備份              | 每天快照 + 交易紀錄（5分鐘上傳S3） | 決定保留期限（最長35天） |
| 故障切換 Multi-AZ | 掛了自動切到 standby               | 設定好就自動             |

**時間點還原（PITR）：砌表砌到 AWS 也救不了？**

1. 交易紀錄每 5 分鐘上傳到 S3（latest restorable time 為準）
2. 拿過去某刻的快照，重播紀錄
3. 還原出來是全新資料庫（原本那台不動；應用改連過去或搬資料回）

**何時不適合用 RDS（回 EC2）**

- 需要登系統、裝清單外外掛
- 用的引擎版本 RDS 不支援
- 軟體按機器授權計費

**交給 RDS，安全就是 AWS 的事？**

- ✗ 常想：受管了，資料庫安全都歸 AWS
- ✓ 實際：誰能連、密碼、加密永遠是你的；帳號權限開太大常比 AZ 掛還嚴重

## 二、Aurora：運算跟儲存分開

**兩台長得很像：一個保命，一個分擔**

|                       | Multi-AZ                  | Read Replica              |
| --------------------- | ------------------------- | ------------------------- |
| **目的**              | 保險：防機器掛、AZ 出事   | 分擔：讀取量大            |
| **同步？**            | ✓ 同步；standby 不能讀    | ✗ 非同步；可以讀          |
| **代價**              | 每次寫入多等一下          | Multi-AZ 是選一種         |
| **怎麼切/升級**       | DNS 改指 standby 成新主要 | 手動 promote 複本變新主要 |
| **要多久**            | 60～120 秒（官方說）      | 不會自動，要人工 promote  |
| **應用改什麼**        | 不改連線但要斷重連        | 要改，複本的新網址        |
| **能救整個 Region？** | ✗ 只救一個 AZ             | 可以跨 Region 部署        |

**關鍵字只有兩個：同步、非同步**

**考題看訊號詞怎麼選**

| 需求                             | 選什麼                               |
| -------------------------------- | ------------------------------------ |
| 高可用、防單一 AZ 出事、自動切換 | **Multi-AZ**                         |
| 讀取量大、報表拖累主庫           | **Read Replica**                     |
| 離海外使用者近、跨區讀           | **跨 Region Read Replica**           |
| Region 掛了也要救回              | **跨 Region Read Replica + promote** |

**Multi-AZ 細節**

- standby 平常啥都不做，只收同步資料
- 何時切：機器掛、AZ 出事、修補、手動重啟並切換
- 代償：多付一台閒置機器錢；換掉的資料不遺失

**Read Replica 細節**

- promote（提升）：複本變獨立可寫資料庫；尚未複到的幾秒會遺失
- 複製延遲（replica lag）：落後的那段是關鍵概念
- 常用場景：報表、搜尋、首頁列表（讀多的操作）

## 三、快取：記下算好的答案

**三件事**

- 先問記憶體，沒有才問資料庫
- 資料庫是正本，快取是會消失的抄本
- 策略只答兩件事：什麼時候抄、能舊多久

**先問記憶體，沒有才問資料庫**

熱門商品一秒被問一千次，小時才變一次；多開 reader 只是讓每台都重算一個答案

|                          | 快取放在資料庫前面（ElastiCache 等） | 打到資料庫                         |
| ------------------------ | ------------------------------------ | ---------------------------------- |
| **命中（cache hit）**    | 直接回，資料庫不用動                 | 查完順手寫回快取                   |
| **沒命中（cache miss）** | 去問資料庫，查完順手寫回快取         | 查完順手寫回快取（下次省快取查詢） |

**快取是會消失的抄本** — 資料庫永遠是正本，快取只是拷貝

**策略只答兩件事：什麼時候抄、能舊多久**

|                | 說法                             | 何時用               |
| -------------- | -------------------------------- | -------------------- |
| **Serverless** | 不挑節點，用多少付多少           | 專題、流量不好預測   |
| **自己挑節點** | 挑機型跟台數，可以買預留         | 流量穩、要壓低單價   |
| **Memcached**  | 單純的大雜湊表、自挑節點版沒複寫 | 純快取、不需資料結構 |

**Valkey 新專案直選**（Redis 改授權後的開源分支）

- 時間線：Valkey 2024 年 3 月出現→ Linux 基金會維護→ AWS 2024 年 10 月推 ElastiCache for Valkey
- 大多寫程式只記兩個網址：寫的一個、讀的一個；最多 15 台 reader

**放進快取，就不會掉了？**

- ✗ 大家通常會想：購物車只存在快取裡，反正記憶體很快
- ✓ 實際上：資料庫是正本，快取只是抄本；Valkey 9.0 以上的節點叢集可開 durability，只救節點掉

**用到才抄，還是一改就抄**

**Cache-Aside（旁路快取 / lazy loading）**

- 讀資料時先查快取，沒有才查資料庫，再存進快取
- 優點：只保有被查過的資料，節省快取空間
- 缺點：首次查詢慢、快取資料可能舊

**Write-Through（寫穿）**

- 寫資料時同時寫資料庫和快取
- 優點：快取永遠最新，下一個人讀直接命中快取
- 缺點：寫入變慢一點

**命中率決定一切** — 命中率從 50% 拉到 90%，資料庫壓力少五倍；數字是示意，算法是真的

## 四、資料庫懂意思，切換要實測

資料庫從「儲存紀錄」升級到「理解意思」，核心在於向量搜索與語義快取的實測

**pgvector 讓 PostgreSQL 具備向量搜索能力**

- `CREATE EXTENSION vector`：開啟向量搜索功能
- 文字嵌入成向量（embedding），依距離排序找最相似的結果
- RDS PostgreSQL 與 Aurora PostgreSQL 都內建 pgvector 擴充

**命中錯誤比沒命中更危險**

| 狀況         | 說法                         | 風險                             |
| ------------ | ---------------------------- | -------------------------------- |
| 多像才算命中 | 距離小於某個臨界值就認定命中 | 相似度門檻太寬，會回傳不對的答案 |
| TTL 與更新   | 退貨政策改了，快取還在舊答案 | 快取過期前，使用者看到過時訊息   |
| 不共用問題   | A 使用者的答案給了 B 使用者  | 問題相似度高，但答案不該共享     |

**語義快取流程**

1. 使用者問題 → 轉成向量
2. 問快取，查相似的舊問題
3. 查到 → 直接回舊答案（秒級，不花 token）
4. 沒查到 → 呼叫模型，存進快取供下次用

**⾨檻怎麼挑：從緊往鬆⼀格⼀格放**

1. **淺 20 對該命中、20 對不該命中**：不該命中的要挑長得像、但是同一問題的句子
2. **從 0.05 開始，每次放寬 0.05**：每放一格，看該命中的命中對、不該命中的有沒有誤中
3. **出現第一對誤中，就退回上一格**：那格的命中率就是收益；太低代表不適合語義快取

**重點**：門檻距離是蛇形距離（<=> 出入来，0 到 2，越小越像），距離小於多少算同一問題是關鍵概念

**Agent 的記憶問題：看掉了要不要緊**

| 用途                            | 實務建議                                       |
| ------------------------------- | ---------------------------------------------- |
| ElastiCache (Valkey)            | 這一輪對話的短期記憶，掉了要不要緊（會重新查） |
| RDS 或 Aurora                   | 要查、要統計、要跟使用者資料 JOIN 的長期紀錄   |
| DynamoDB / AgentCore 的記憶功能 | 後面的單元再比較                               |

**文件向量重複算要花時間，掉了會痛，放資料庫；對話記憶掉了不痛，放快取。**

## 五、實作：手動切一次，記下斷了幾秒

一台小機器每秒寫一筆，印 ok 或失敗；你按下切換，記下失散那段，最後查資料有沒有少

**必做：七步就及格（70%）**

1. **用戶端**：EC2 t3.micro (db-client)、Amazon Linux 2023、User data 裝 mariadb105、IAM 選 ec2-ssm-role
2. **建資料庫**：RDS MySQL、Multi-AZ deployment、db.t4g.micro、Managed Secrets Manager、Storage gp3 20 GiB
3. **接上用戶端**：RDS Connectivity 選 Connect to EC2、挑 db-client、Initial database 填 labdb
4. **拿連線資訊**：複製 Endpoint、記下 Availability Zone、從 Secrets Manager 拿 password
5. **開始寫**：Session Manager bash 跑迴圈，每秒 INSERT 並印時間與 ok/失敗
6. **手動切**：看到「失敗」出現，RDS 按 Reboot with failover，記錄何時開始斷連、何時恢復
7. **對帳**：計斷裂秒數（恢復後第一個 ok 減失敗前最後一個 ok），查 COUNT 確認資料筆數，找 timestamp 「空洞」位置

**進階（20%）與加分（10%）**

- **進階**：查 RDS Logs & events 找「failover started / completed」時間戳，與第 4 步記的 AZ 對比，確認主機房確實從（如）ap-northeast-1a 換到 1b
- **加分**：TRUNCATE 表清空，Reboot 不勾 failover 再測一次當對照組，比較兩次秒數、AZ 變化、官方記錄是否提到資料遺失

**實作繳交：兩張截圖 + 一句對帳**

1. **截圖 1**：bash 執行過程（每秒時間、ok 與失敗混合、中間一段「失敗」）
2. **截圖 2**：SELECT 查詢結果（COUNT 數字、最後幾筆 timestamp）
3. **一句對帳**：「中斷 XX 秒（HH:MM:SS～HH:MM:SS）；失敗 YY 筆，官方記錄 ZZ 秒」

## 六、回家作業：拿期末專題來做，一律個人完成(略，參考用)

1. **在期末專題的 RDS 上實作高可用**
   - 建 Multi-AZ（同步備援）或跨 Region Read Replica（異地讀取）
   - 測試故障轉移過程

2. **實作讀寫分離**（若有高讀取量）
   - 讀查詢打到 Read Replica
   - 寫操作打到主庫
   - 觀察 replica lag 影響

3. **設定備份與還原**
   - 快照保留期限
   - 時間點還原測試（砌掉資料後還原）

4. **記錄並分析**
   - RDS 配置細節（AZ、引擎版本、執行個體類型）
   - 故障切換耗時
   - 成本評估（Multi-AZ 雙倍 / Read Replica 額外費用）
