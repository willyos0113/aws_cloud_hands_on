# d17 | 事件驅動架構：用訊息連接服務，不一直等對方

> 來源：`lectures/D17 事件驅動架構 投影片.pdf`（共 35 頁；講義封面標示為「第 14 單元」；規格為講義 2026-10-19 查閱的數字，出處為 SQS、SNS、EventBridge、Lambda 官方文件）

**今日目標**：下單之後要寄信、產報表、轉檔，誰來等？用佇列把服務解耦，下游掛了訊息也不消失，並知道失敗的訊息會去哪裡。

## 一、緩衝層：同步呼叫一掛，全部一起掛

**三件事**

- 慢工作丟進佇列，上游不用等下游
- 下游掛了，訊息留在佇列等它回來
- 工作者＝背景拿訊息做事的程式；兩邊解耦

**佇列緩衝 vs 同步呼叫**

| 項目     | 佇列緩衝                     | 同步呼叫            |
| -------- | ---------------------------- | ------------------- |
| 流程     | 下單 → 佇列 → 寄信           | 下單 → 直接呼叫寄信 |
| 寄信變慢 | 下單不受影響                 | 下單跟著慢          |
| 寄信掛了 | 訊息留在佇列，恢復後接著處理 | 下單失敗            |

**CCP 考點**

- 應用程式之間互傳訊息、解耦 → **Amazon SQS**；Auto Scaling 調整資源數量、ELB 分配流量、Kinesis 處理大量資料流，都是誘答（題庫 CLF-C02 第 0081 題）

> 一句話：慢工作丟進佇列，上游不用等下游。下游掛了，訊息留在佇列等它回來。

## 二、佇列型態：順序和重複怎麼選

**三件事**

- 標準佇列：至少一次，可能兩份
- FIFO：同 group 內依序
- 標準佇列的處理邏輯要能重複執行

**標準或 FIFO**

| 項目     | 標準佇列           | FIFO（先進先出）                     |
| -------- | ------------------ | ------------------------------------ |
| 送達     | 至少一次，可能兩份 | 同一去重 ID 重送，5 分鐘內不新增副本 |
| 順序     | 盡力而為           | 同 group ID 內依序                   |
| 同時處理 | 不分 group         | 同 group 前一批處理完才給下一批      |
| 吞吐量   | 幾乎不限           | 有上限                               |
| 名稱     | 任意               | 結尾 `.fifo`                         |

**需求訊號詞 → 選什麼**

| 訊號詞         | 選擇 |
| -------------- | ---- |
| 要順序、不重複 | FIFO |
| 要吞吐、能重複 | 標準 |

**CCP 考點**

- 傳送、儲存、接收訊息，且要 FIFO 順序 → **SQS**；Step Functions 是協調工作流程、Kinesis 處理資料流（題庫第 0188 題）

> 注意：題庫詳解稱 SNS 不支援 FIFO，但官方現在已有 SNS FIFO，**考試答案照題庫**。SNS 是推送，儲存靠 SQS。

> 一句話：要順序、不重複選 FIFO，要吞吐、能重複選標準。

## 三、可見性與死信：保護期要夠長，失敗要隔離

**三件事**

- 收到訊息後進入保護期（可見性逾時）
- 沒刪除，訊息會重現
- 反覆失敗的送死信佇列，修好再搬回

**可見性逾時（保護期）：太短重複、太長變慢**

| 步驟 | 動作                                         |
| ---- | -------------------------------------------- |
| 收到 | `ReceiveMessage`，訊息變不可見（預設 30 秒） |
| 完成 | `DeleteMessage` 才會消失；沒刪就重現         |

- **處理時間比保護期長：別人又收到同一則，同一封信寄兩次**
- 保護期太長則是失敗後要等很久才重試

**死信佇列：反覆失敗的訊息搬去隔離**

| 概念           | 意思                                                  |
| -------------- | ----------------------------------------------------- |
| redrive policy | 來源佇列的設定：超過 `maxReceiveCount` 就搬去死信佇列 |
| 死信佇列       | SQS 自動搬入                                          |
| redrive        | 修好之後，你下指令把訊息搬回來                        |

> 一句話：保護期設得比處理時間長，反覆失敗的送死信佇列，修好再 redrive 搬回來。

## 四、扇出：每個下游有自己的佇列

**三件事**

- 一對多用 SNS 加 SQS
- SNS 推，SQS 拉，每個下游照自己的速度處理
- filter policy 讓每個佇列只收自己要的

**扇出加緩衝**

- 一則訂單事件 → SNS 主題 → 寄信佇列、報表佇列、轉檔佇列（各自的工作者）

**訊息過濾：每個佇列只收需要的**

```json
{ "task": ["report"] }
```

- 這是訂閱的 filter policy
- `task` 是**發布時附的訊息屬性**，不在本文裡
- 值寫成陣列，符合其中任一個就收
- 範例：發布時 `task=report` → 報表佇列收；`task=convert` → 報表佇列不收

**CCP 考點**

- 發佈者（publisher）與訂閱者（subscriber）的組合 → **Amazon SNS**；Lambda 執行程式碼、CloudWatch 監控、CloudFormation 用範本建資源（題庫第 0376 題）

> 一句話：一對多用 SNS 加 SQS，各有各的佇列，再用 filter policy 讓每個佇列只收自己要的。

## 五、事件與排程：模式比對，或按時間觸發

**三件事**

- EventBridge：事件 → 規則 → 目標
- 事件用模式比對
- 時間用 cron 或 rate

**事件模式：長得和事件一樣的規則**

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": { "state": ["terminated"] }
}
```

- 多個值（陣列）：任一符合就算

**排程：固定間隔或指定時間**

| 類型 | 用在         | 官方例子              |
| ---- | ------------ | --------------------- |
| rate | 固定間隔     | `rate(20 minutes)`    |
| cron | 指定時間日期 | `cron(0 8 ? * 2#1 *)` |

- 規則符合才送到目標
- 舊的排程規則（legacy）官方建議改用 **Scheduler**

**CCP 考點**

- EC2 進入 `stopping` 狀態時觸發 Lambda → **EventBridge**；SNS 要先有人發布訊息，Config 追蹤組態合規，CloudFormation 建資源（題庫第 0502 題）

> 一句話：事件用模式比對，時間用 cron 或 rate，規則符合才送到目標。

## 六、部分成功：批次只重試失敗的

**三件事**

- Lambda 從 SQS 拿一批訊息，預設有一則失敗就整批重來
- 開啟 `ReportBatchItemFailures` 只重試失敗的
- 函式要回傳失敗的訊息 ID

**預設 vs 回報個別失敗**

| 項目     | 預設                    | 回報個別失敗                      |
| -------- | ----------------------- | --------------------------------- |
| 範例     | 同一批 5 則             | 寄信批次 5 則：3 則成功、2 則失敗 |
| 重新可見 | 整批 5 則               | 只有失敗的 2 則                   |
| 副作用   | 成功的 3 則也會再做一次 | 成功的不重做                      |

- 開啟方式：**事件來源對應（event source mapping）** 設 `ReportBatchItemFailures`

**函數回傳：失敗的訊息 ID**

```json
{
  "batchItemFailures": [
    { "itemIdentifier": "id2" },
    { "itemIdentifier": "id4" }
  ]
}
```

- 範例：id1 到 id5 一批，id2、id4 失敗
- `itemIdentifier` 填 `messageId`

> 一句話：批次要只重試失敗的：回傳 `batchItemFailures`，例外全接起來，別讓整批重來。

## 七、實作：讓失敗訊息不消失

流程：注入 100 則（含 10 則必失敗）→ SNS `orders` 扇出 → `convert-q` → Lambda 工作者 → 失敗的由 SQS 搬入 `convert-dlq`。`mail-q` 是另一個下游，不接工作者。講義未標區域與預期費用，動手前先向講師確認；本實作為講師自擬題目。

**驗收：90＋10＝100**（成功 90 則加死信 10 則，等於注入的 100 則）

**必做：六步**

1. **建三個佇列**：僅 `convert-q` 設 redrive，最多收 3 次
2. **建主題 `orders`**，訂閱兩個佇列
3. **建 IAM 角色與函數**
4. **事件來源對應開 `ReportBatchItemFailures`**：可見性逾時 60 秒 ＞ 函數逾時 10 秒
5. **注入 100 則**，其中 10 則必失敗
6. **驗收，再重放**（redrive）

**清理：做完一定要刪，順序依資源相依關係**

1. 刪事件來源對應與函數
2. 刪 SNS 訂閱與主題
3. 刪三個佇列
4. 刪日誌群組與 IAM 角色
5. `list-queues` 查不到佇列

## Takeaway

1. 慢工作丟進佇列，上游不用等下游，下游掛了訊息留著
2. 要順序選 FIFO，要吞吐選標準；標準佇列的處理邏輯要能重複執行
3. 可見性逾時要大於處理時間，反覆失敗送死信佇列，修好再 redrive
4. 一對多用 SNS 加 SQS 加 filter policy；批次要回傳 `batchItemFailures`
