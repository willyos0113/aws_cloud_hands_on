# d12 | 可觀測性與稽核：CloudWatch、CloudTrail 與 EventBridge

> 來源：`lectures/D12 可觀測性與稽核.pdf`（共 69 頁；定價與額度為講義 2026-10-01 查閱的數字，Config、X-Ray 為 2026-10-02）

**今日目標**：凌晨三點機器 CPU 衝到 100%，你在睡覺，系統要自己叫醒你、留下證詞、查得出是誰動的手。

**四個工具，各答一個問題**

| 工具        | 回答什麼                           | 比喻               |
| ----------- | ---------------------------------- | ------------------ |
| CloudWatch  | 它現在健不健康（指標、日誌、告警） | 體溫計加鬧鐘       |
| CloudTrail  | 誰在什麼時候動了它                 | 帳號裡的監視器錄影 |
| AWS Config  | 設定合不合規定、資源現在長怎樣     | 設定的健檢表       |
| EventBridge | 事件一發生就自動處理               | 錄影上裝的感應器   |

## 一、指標與告警：讓系統自己叫醒你

**三件事**

- 服務自己把數字送進 CloudWatch
- 記憶體與磁碟要裝 agent 才看得到
- 告警「N 點中 M 點」超標才響，且只在換狀態那一刻動作

**資料流**：EC2 交數字 → CloudWatch 記下來 → 告警比門檻 → SNS 寄信叫醒你

**指標：一個有地址的數字串**

| 四格     | 意思       | 例                  |
| -------- | ---------- | ------------------- |
| 命名空間 | 哪個資料夾 | `AWS/EC2`           |
| 指標名稱 | 量什麼     | `CPUUtilization`    |
| 維度     | 哪一台     | `InstanceId=i-0abc` |
| 統計     | 怎麼濃縮   | 5 分鐘平均          |

- 四格合起來才確定一條線；**換一個 InstanceId，就是另一條線**

**CloudWatch agent：記憶體要從裡面送出來**

| 指標                | 預設有嗎 | 說明                      |
| ------------------- | -------- | ------------------------- |
| CPU、網路、狀態檢查 | 有，免費 | AWS 從外面量得到          |
| 記憶體、磁碟空間    | 沒有     | 要在機器裡裝 agent 送出來 |

- 一句話：EC2 這支體溫計只量得到用了多少電，量不到冰箱塞多滿

**告警：看最近 N 點，有 M 點超標才響**

以門檻 80、每點 5 分鐘、最近三點 85、90、70 為例：

| 規則        | 結果  | 原因                    |
| ----------- | ----- | ----------------------- |
| 3 點中 3 點 | OK    | 70 沒超標，只有兩點超標 |
| 3 點中 2 點 | ALARM | 兩點超標就夠            |

- 每個點**各自**比門檻，不會先平均再比（85、90、70 平均 81.7 不能拿來判斷）

**告警狀態：只在換狀態那一刻動作**

| 狀態              | 意思             | 動作           |
| ----------------- | ---------------- | -------------- |
| INSUFFICIENT_DATA | 剛建好、資料不夠 | —              |
| OK                | 在門檻內         | 恢復時可設動作 |
| ALARM             | 越過門檻         | 變壞那一刻動作 |

- 一直停在 ALARM，**不會一直寄信**
- 例外：Auto Scaling 動作每分鐘會再觸發

**SNS：告警認主題，不認人**

- 主題（topic）：廣播頻道；訂閱：誰收、怎麼收
- **坑**：email 訂閱要到信箱按 Confirm，狀態變 Confirmed 才收得到
- 「認主題不認人」為講師經驗

**免費額度：課堂練習的量都在裡面**

| 項目               | 免費額度      |
| ------------------ | ------------- |
| 基本監控指標       | 全部          |
| 自訂指標加詳細監控 | 10 個         |
| 標準解析度告警     | 10 個         |
| SNS 寄 email       | 每月 1,000 則 |

- Free plan：先吃免費額度，超過的用註冊點數付，期間不會產生費用

**檢查點：門檻 CPU ≥ 80、3 點中 3 點超標才響，最近三點 85、90、70，狀態是？**

- ✓ OK：三點要全部超標
- ✗ 選「ALARM，兩點超過 80」：把「3 點中 2 點」的規則套錯
- ✗ 選「ALARM，平均 81.7」：每個點各自比門檻，不會再平均

> 一句話：體溫計量得再準，也不會叫醒你；叫醒你的是鬧鐘。

## 二、日誌：告警說出事了，日誌說出了什麼事

**三件事**

- 日誌送出機器，集中放進 CloudWatch Logs
- Logs Insights 用管線指令撈例外
- 指標篩選器把文字變回數字，接上告警

**為什麼要集中送出**

|               | 機器被砍後         | 十台機器     |
| ------------- | ------------------ | ------------ |
| SSH 進去 grep | 日誌跟著消失       | 要 grep 十次 |
| 集中送出      | 機器走了，日誌還在 | 一處查完     |

**log group：機器會換，group 不換**

| 層級       | 意思                      | 例                                           |
| ---------- | ------------------------- | -------------------------------------------- |
| log event  | 一行：時間加訊息          | `10:00:03 ERROR NullPointer…`                |
| log stream | 同一個來源的一串 event    | `i-0abc`（這台）、`i-0def`（明天換的新機器） |
| log group  | 一組 stream，設定都掛這裡 | `/web/app`：保留期、權限、指標篩選器         |

**Logs Insights：一萬行進去，管線剩 20 行**

```
fields @timestamp, @message          # 選要看的欄位；@ 開頭是自動欄位（時間、原始訊息）
| filter @message like /Exception/   # 只留含 Exception 的行
| sort @timestamp desc               # 新的在前
| limit 20                           # 只取 20 行
```

- `|`：前一節的結果交給下一節
- `stats`：分組計數，例如 `stats count(*) by bin(1h)` 算每小時幾筆
- 不會寫：主控台能用自然語言產生查詢，**但一定要在真實日誌上跑一次**確認

**日誌費用：不設保留期，日誌永遠留著**

- ✗ 大家通常會想：留著又不會怎樣
- ✓ 實際上：預設 Never Expire，存放費一直算；在 group 上設天數，到期標記刪除，之後不再算存放費

| 項目     | 說明                                             |
| -------- | ------------------------------------------------ |
| 免費額度 | 每月 5 GB，寫入、存放、查詢掃描共用              |
| 省錢     | 查詢照**掃過的量**算：選對 group、時間範圍選最窄 |

**指標篩選器：把文字變回數字，接上告警**

- 對到 `ERROR` 一行，`ErrorCount` 記 1；沒對到送預設值 0
- **坑**：不會回頭算，出事後才補，那次補不回來

**檢查點：每小時有幾個例外，哪個查詢對？**

- ✓ `filter @message like /Exception/ | stats count(*) by bin(1h)`：先篩出例外再分小時數
- ✗ `stats` 在前：stats 之後只剩時間與計數，沒有 `@message` 可篩
- ✗ `limit 1h`：`limit` 是筆數不是時間

**CCP 考點**

- CLF-C02 第 0302 題：EC2 已無法存取、也不在主控台，要判斷是什麼動作造成 → **CloudTrail**（查得到誰呼叫 `TerminateInstances`）
- 誘答：CloudWatch Logs 說得出「我這行炸了」，說不出「誰把我砍掉」；Security Hub 彙整發現、Inspector 掃漏洞，都不記操作
- 看到「什麼動作／誰做的」→ CloudTrail

> 一句話：日誌不能跟機器住在一起，不然機器一走，證人也跟著走。

## 三、稽核：機器好好的，是誰動了它

**三件事**

- CloudTrail 記下帳號裡每一次操作
- 改設定是管理事件，動資料是資料事件
- 三條記錄路線：Event history、trail、S3 存取日誌

**每一筆事件記四件事**

| 問題   | 欄位              |
| ------ | ----------------- |
| 誰     | `userIdentity`    |
| 何時   | `eventTime`       |
| 做什麼 | `eventName`       |
| 從哪裡 | `sourceIPAddress` |

**事件分類：換門鎖要記，每次進出要另外開**（比喻為講師說法）

| 類別     | 記什麼 | 例             | 預設與費用                         |
| -------- | ------ | -------------- | ---------------------------------- |
| 管理事件 | 改設定 | 開 22 埠       | trail 預設記，第一份免費           |
| 資料事件 | 動資料 | S3 `GetObject` | **預設不記**，每 10 萬筆 0.10 美元 |

**記錄路線：免費錄影、長期存檔、門口登記簿**

|        | Event history                                                      | Trail                                                         | S3 access logs           |
| ------ | ------------------------------------------------------------------ | ------------------------------------------------------------- | ------------------------ |
| 設定   | 開帳號就有，免費                                                   | 自己建，存進你的 S3 桶                                        | 在桶上開                 |
| 記什麼 | 近 90 天**管理事件**                                               | 預設管理事件，可開資料事件                                    | 這個桶的請求，含驗證失敗 |
| 限制   | 每區一份；只有管理事件；一次一個屬性過濾；預設只顯示有改東西的事件 | 主控台建的是多區域；organization trail 可記全組織（講師示範） | 盡力送達，可能漏記       |

- 官方建議稽核優先用 CloudTrail

**檢查點：主管問「上週誰下載了桶裡的 report.pdf」，你沒建過 trail、桶也沒開存取日誌**

- ✓ 查不到：要事先開，事後補不回來
- ✗ 去 Event history 查 `GetObject`：`GetObject` 是資料事件，Event history 只有管理事件
- ✗ 現在建 trail 會補回上週：記錄從開啟那一刻才開始

**三個工具的分工**

| 問題               | 用什麼     |
| ------------------ | ---------- |
| 它現在健不健康     | CloudWatch |
| 設定合不合規定     | AWS Config |
| 誰在什麼時候動了它 | CloudTrail |

- 兩個常一起用：Config 說 Security Group 何時從關變開，CloudTrail 說是誰開的

**CCP 考點**

- CLF-C02 第 0612 題：法遵需求，記錄並**評估組態變更**，並能對資源執行**補救動作** → **AWS Config**（記錄設定變化、對照規則檢查合規、可接自動補救）
- 誘答：CloudTrail 回答「誰呼叫了哪個 API」，不評估合規
- CLF-C02 第 0654 題：昨天多個資源被刪，找原因並判定哪位使用者刪的 → **CloudTrail**（Event history 用時間或 `Delete` 開頭過濾，看 User name）
- 誘答：GuardDuty 找可疑行為發警報，不回答誰刪的；Inspector 掃漏洞；Trusted Advisor 給建議

> 一句話：指標告訴你機器怎麼了，CloudTrail 告訴你是誰動了它。
> 22 埠誰開的：去那一區的 Event history。S3 檔案誰下載的：要事先開，沒開就沒記。

## 四、EventBridge：錄影上裝感應器

**三件事**

- 事件進 bus，規則比對，目標做事
- API 呼叫事件要有 trail，修復別抓到自己
- 樣式抓不到的開法，交給 AWS Config

**三個角色**

| 角色      | 意思                 |
| --------- | -------------------- |
| Event bus | 帳號預設的事件收件匣 |
| Rule      | 什麼事件要送去哪     |
| Target    | 收到後真正做事       |

**事件樣式：長得跟事件一樣，值放陣列**

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["ec2.amazonaws.com"],
    "eventName": ["AuthorizeSecurityGroupIngress"],
    "requestParameters": {
      "ipPermissions": {
        "items": {
          "fromPort": [22],
          "ipRanges": { "items": { "cidrIp": ["0.0.0.0/0"] } }
        }
      }
    }
  }
}
```

- 事件的值等於陣列裡任一個，就算對到
- 寫了的每一欄都要對到；只開給公司網段，不觸發
- **漏洞**：開 0 到 65535 整段，`fromPort` 是 0，`[22]` 對不到（`items` 寫法與範圍例子為講師經驗）

**EventBridge 的兩個坑**

| 坑                       | 說明                                              |
| ------------------------ | ------------------------------------------------- |
| 沒有 trail，什麼都沒發生 | API 呼叫要送進 bus，**一定要有啟用中的 trail**    |
| 修復又觸發自己           | 樣式寫精準，修復用的 API 別被自己抓到（無限迴圈） |

**Target：寄信、跑修復腳本，或一段程式**

| Target         | 做什麼                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------ |
| SNS            | 寄信給值班的人                                                                             |
| SSM Automation | 跑 AWS 寫好的 runbook，例如 `AWS-DisablePublicAccessForSecurityGroup` 關掉對全世界開的 SSH |
| Lambda         | 跑你的程式（第 14 單元教）                                                                 |

- 做法：**先通知，確定抓得準，再升級成自動撤銷**

**AWS Config：看資源現在長怎樣**

- 受管規則 `restricted-ssh` 直接看入站規則，補上「整段開放」這種事件樣式抓不到的洞
- 沒有免費額度，講師示範（參考 Maarek SAA-C03 講義）

**檢查點：規則抓 `AuthorizeSecurityGroupIngress`、目標是 SNS，開了 22 埠卻沒收到信，Event history 看得到那筆事件，最可能缺什麼？**

- ✓ 沒有開著記錄的 trail：Event history 有，trail 沒有
- ✗ 要改用 Custom Event Bus：CloudTrail 事件只送到 default event bus
- ✗ SNS 不能當目標：SNS 主題就在目標清單裡
- ✗ 要先開 EC2 詳細監控：那是第一段的指標，跟事件路由無關

**CCP 考點**

- CLF-C02 第 0502 題：EC2 進入 `stopping` 狀態時觸發 Lambda → **Amazon EventBridge**
- 誘答：Config 記設定變化；SNS 只發通知，不會看著 EC2 自己動
- EC2 狀態變化是 EC2 自己送的事件，**不必靠 trail**（對比：API 呼叫事件才要 trail）

> 一句話：CloudTrail 是錄影。EventBridge 是在錄影上裝感應器，有人一碰，警鈴就響。

## 五、AI 應用的可觀測性：答錯也回 200

**三件事**

- 呼叫模型是管理事件，查得到誰，看不到內容
- 盯 token、首字延遲、防護欄，CPU 不再是重點
- AI 答錯回 200，要看內容與使用者反應

**CloudTrail：呼叫模型記成管理事件**

| 類別     | 動作                                                                         | Event history                   |
| -------- | ---------------------------------------------------------------------------- | ------------------------------- |
| 管理事件 | `InvokeModel`、`InvokeModelWithResponseStream`、`Converse`、`ConverseStream` | 看得到，免費留 90 天            |
| 資料事件 | `InvokeAgent`、`Retrieve`、`ApplyGuardrail`（Agent、知識庫、防護欄）         | 看不到，要在 trail 另開、另付費 |

- 名字不用背，記一句：**呼叫模型是管理事件**。直覺會猜資料事件，這題要查文件

**InvokeModel 紀錄：誰、何時、哪個模型都在，內容不在**

- 有：`userIdentity`（誰）、`eventTime`（何時）、`modelId`（哪個模型）
- 沒有：提示和回答的內容（`responseElements: null`）
- 要留問與答，另開 **model invocation logging**：預設關閉，送 CloudWatch Logs 或 S3

**Bedrock 指標：換一批數字盯，CPU 不再是重點**

- ✗ 天真做法：盯你機器的 CPU。模型在 Bedrock 跑，你的機器只轉送，CPU 閒得很，使用者卻等了十秒

| 想知道               | 看哪個指標                                  |
| -------------------- | ------------------------------------------- |
| 用了多少 token（錢） | `InputTokenCount`、`OutputTokenCount`       |
| 多久看到第一個字     | `TimeToFirstToken`                          |
| 被擋或出錯           | `Throttles`、`ClientErrors`、`ServerErrors` |
| 防護欄出手幾次       | `InvocationsIntervened`                     |

**TimeToFirstToken：使用者盯的是第一個字**

| 指標                                     | 使用者感受                  |
| ---------------------------------------- | --------------------------- |
| `TimeToFirstToken` 前三秒一片空白        | 空白 3 秒，使用者按重新整理 |
| `InvocationLatency` 幾十秒，但字一直在出 | 使用者可以接受              |

- `TimeToFirstToken` 只有串流 API 有；不用串流，就只能看整段延遲

**追蹤：整段 8 秒，慢在哪一站**

- 一個請求經過：你的 API → Retrieve（檢索）→ Model → Tool → Model，要知道哪一站慢
- **X-Ray**：把每一站花多久串成一條線
- 轉向 OpenTelemetry：X-Ray SDK 2026-02-25 起進入維護模式（五站與各站長短為講師示意）

**AI 的故障：答錯時每一步都回成功**

|          | 傳統 bug     | AI 答錯    |
| -------- | ------------ | ---------- |
| 狀態碼   | 500          | 200        |
| 日誌     | 有 Exception | 乾淨       |
| 指標     | 錯誤數上升   | 全部正常   |
| 誰先發現 | 告警         | **使用者** |

**答案品質：三層做法，由便宜到貴**

| 層  | 做法         | 內容                                            |
| --- | ------------ | ----------------------------------------------- |
| 1   | 留下問與答   | 開 model invocation logging，每天抽幾十筆人工看 |
| 2   | 收使用者回饋 | 讚與倒讚，倒讚次數做成自訂指標接告警            |
| 3   | 盯間接訊號   | 工具失敗、防護欄介入率突然變化                  |

- 怎麼系統化評估答案品質，後面單元再講

**檢查點：客服機器人把退貨期限講成 60 天（正確是 7 天），5xx 是 0、日誌沒有 Exception、CPU 正常，哪個做法最可能及早發現？**

- ✓ 開 invocation logging 抽查，倒讚數接告警：看內容與使用者反應
- ✗ 調低 CPU 告警門檻、開 EC2 詳細監控：還在量機器的體溫，模型不在上面跑
- ✗ 對 Exception 建指標篩選器：在找有沒有出錯，這次每一步都成功了

> 一句話：傳統系統壞了會尖叫，AI 壞了會微笑著回你 200。
> 誰叫了哪個模型：Event history 查得到，看不到內容。該盯的數字：token、首字延遲、防護欄。

## 六、實作：告警、日誌、稽核串起來

不開機器，**必做預期 0 元**。全程在 Tokyo 區域用 CloudShell 操作，最後的 Event history 以 `course-admin` 身分查。講義只列必做，沒有進階與加分。

**三個目標**

- 收到一封真的告警信
- Logs Insights 撈出兩個例外
- 抓出開 22 埠的人就是你

**必做：六步**

1. **開 CloudShell、建 SNS**：Tokyo 開 CloudShell；SNS 建主題 `obs-lab-alerts`，Email 訂閱 → 到信箱按 Confirm，狀態 Confirmed
2. **建日誌群組**：貼第一段指令，建 `/obs-lab/app`，沒有錯誤訊息
3. **ERROR 變指標接告警**：貼第二段，Alarms 出現 `obs-lab-errors`（**一定要在第 4 步之前**，篩選器不會回頭算）
4. **寫日誌**：貼第三段，寫六行日誌，其中兩行 ERROR；1 到 3 分鐘內收到告警信（時間為講師預估）
5. **Logs Insights**：選 `/obs-lab/app`，撈 `Exception`，看到兩列例外

## Takeaway

1. 體溫計量得再準也不會叫醒你，叫醒你的是鬧鐘
2. 日誌不能跟機器住在一起，不然機器一走，證人也跟著走
3. CloudTrail 是錄影，EventBridge 是錄影上的感應器
4. 傳統系統壞了會尖叫，AI 壞了會微笑著回你 200
