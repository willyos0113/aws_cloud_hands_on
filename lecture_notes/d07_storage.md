# d07 - 儲存 EBS、EFS 與 S3

[內容]

## 一、三種儲存的形狀：區塊、檔案、物件

|       | EBS（區塊） | EFS（檔案）       | S3（物件）       |
| ----- | ------- | ------------- | ------------ |
| 給誰用   | 一台機器    | 同 Region 的很多台 | 任何地方，走 HTTP  |
| 你看到什麼 | 一顆硬碟    | 一個掛載的資料夾      | 一個桶，用名字拿東西   |
| 改檔案中間 | 可以      | 可以            | 不行，整個檔重傳     |
| 適合    | 開機碟、資料庫 | 共享上傳目錄、模型權重   | 文件、圖片、備份、資料湖 |

- 分界線：多台要不要同時寫、要不要改檔案中間；兩個都要就是 EFS
- 一句話：EBS 一台一顆用，EFS 多台共用用，S3 沒有樹狀結構只有 Key

## 二、EBS：插在牆上的硬碟

- 區塊儲存（block storage）：作業系統看到一顆空硬碟，自己格式化、自己管檔案系統；跟本機硬碟的差異是「硬碟不在機器裡，在網路另一端」，機器透過網路讀寫
- **磁碟綁在一個 AZ**：EBS 只能掛給同一個 AZ 的機器；要到別的 AZ、跨 Region、跨帳號搬資料，都得先拍 **Snapshot** 再還原成新磁碟
- Snapshot（快照）三個重點：**增量存放**（第二張起只存跟上一張不同的區塊，不會每天付全額）、**放在 S3 但主控台看不到那個桶**（只能從 EC2 那邊管）、**是 Region 層級的東西**（還原時 Region 裡任何 AZ 都能選）；加密用 **KMS** 的金鑰，開不開是自己的事
- 機器停了/終止了，資料去哪：**機器停止**＝EBS 磁碟還在，資料照舊；**機器終止**＝資料碟預設留著、開機碟預設跟著刪（看 `DeleteOnTermination` 旗標）；**Instance Store**＝機型自帶的暫存碟，機器停止或終止就清空，資料庫/上傳檔不該放
- 常見誤解：磁碟放在 AWS，AWS 不會自動幫你每天備份；備份是自己的責任，自己定期拍 Snapshot，或用 Data Lifecycle Manager、AWS Backup 排程；開了加密不等於有備份，加密跟備份是兩件事
- 磁碟類型：先 **gp3**（預設款，效能跟容量分開買，3000 IOPS/125 MiB/s 基準，開機碟、一般應用、多數資料庫都夠，每 GiB 可加買到 500 IOPS）→ 數字不夠再買 **io2 Block Express**（買多少 IOPS 就給多少，平均延遲 500 微秒以下，關鍵資料庫、延遲一抖就出事才用）；**gp2**（上一代，效能綁容量，新專案不要選）
- IOPS（每秒讀寫次數，資料庫在意）vs 吞吐 throughput（每秒搬幾 MiB，大檔在意）

## 三、EFS：一份大家掛

- EFS 走 **NFS**（Network File System，透過網路掛遠端資料夾的老協定），機器上看到的就是一個資料夾；能掛的不只 EC2：ECS、EKS 的容器、Lambda、Fargate 都能掛
- 跟 EBS 的差異：EBS 一對一（兩台要共用檔案得自己同步，而且會打架）；EFS 一份大家掛，同一個 Region 的 VPC 內，多台機器跨 AZ 同時讀寫、同時讀寫容量自動長大縮小、用多少付多少不用先買容量
- **每個 AZ 一個 mount target**（掛載點），機器掛自己 AZ 的那個；File system type 分兩種：**Regional**（放多個 AZ，官方推薦，每個 AZ 都建一個掛載點不用錢）、**One Zone**（只放一個 AZ，便宜，但 AZ 掛了就一起掛）
- 計費跟 EBS 對照：EBS 開多大付多大（開 100 GiB 用 5 GiB 也付 100，效能要加買 IOPS 另計）；EFS 用多少付多少（沒有最低費用，預設彈性吞吐、讀寫多少付多少），單價是三種儲存裡最高的；EFS 也有三層冷資料分層，可設多久沒碰自動降層，EBS 沒有分層
- 實務判斷：上傳目錄、共享權重放 EFS；長期備份、訓練資料集轉放 S3
- 題庫常拿兩個表親干擾：看到 **Windows/SMB**（Server Message Block）要選 **FSx for Windows File Server**，EFS 是 NFS 只給 Linux 用；地端要把檔案放進 S3，選 **Storage Gateway** 的 file gateway，用 NFS 協定把檔案寫進 S3

## 四、S3 物件儲存：桶、Key、版本

- **bucket（桶）** 名字全 AWS 分區唯一；**object（物件）** 是檔案本體加 Metadata；**Key** 是物件的完整名字——S3 沒有資料夾，只有一個桶、一堆 Key
- 主控台裡的「資料夾」不是真的存在：一般用途的桶是扁平的，如 `photos/2017/example.jpg` 整串就是一個名字，`photos/` 只是前綴（prefix），斜線是你自己選的分隔符；按 `Create folder` 時主控台其實是替你放了一個 0 位元組、名字叫 `docs/` 的物件
- 改檔案只能整個重新 PUT，一次 PUT 最大 5 GB，更大要分段上傳
- Metadata 三種，上傳那一刻要想好：
  - **系統定義**：大小、時間、儲存類別、ETag（S3 自己給，有些會隨操作變）
  - **使用者定義**：如 `x-amz-meta-owner: leo`（你上傳時給，上傳後不能改，只能複製一份新的）
  - **標籤（tag）**：如 `project=agent`（你隨時給，隨時可改，能管權限跟成本）
- **版本控制（Versioning）**三種狀態，開了只能暫停：
  - 未啟用（預設）：同名覆蓋就沒了，此時物件版本 ID 是 `null`
  - 啟用：同一個 Key 每次上傳都留一版，開了就回不去「未啟用」
  - 暫停：停止累積新版本，舊版本還在——唯一能退的一步
- 啟用後刪除只是蓋一張**刪除標記**（delete marker，沒有內容的版本，讓 GET 回 404），底下的版本都還在、都算錢；把刪除標記刪掉（永久刪除該標記），檔案就回來了；真的要清掉舊版本要用 Lifecycle 的「非目前版本 N 天後過期」
- 補充：
  - 尚硅谷AI培训学校（中國的資策會）
  - Github 架靜態網站（類似 S3 靜態文件的功能）

## 五、儲存類別與 Lifecycle（越冷越便宜，拿回來越慢）

- 溫度階梯：整體趨勢是每 GB 單價越低、取回越慢、最低住宿天數越長，Lifecycle 讓物件自己往下走，**轉類別只能往冷走，不能往回**
- 毫秒就拿得到的四個類別，差在最低天數：

| 類別                | 給什麼資料                                                                      | 最低天數             |
| ------------------- | ------------------------------------------------------------------------------- | -------------------- |
| Standard            | 一個月碰不只一次                                                                | 無                   |
| Standard-IA         | 一個月碰一次，但要立刻拿到（另收每 GB 取回費）                                  | 30 天                |
| One Zone-IA         | 同上，但只放一個 AZ、壞了能重做                                                 | 30 天                |
| Intelligent-Tiering | 不知道會怎麼用就交給它，30 天沒碰自動降到 IA 層、90 天再降到 Archive Instant 層 | 無（收每物件監控費） |

- Glacier（封存 archival）：物件不能直接 GET，要先發 restore 請求解凍出一份暫時副本，只有 **Instant** 直接拿：

| 類別                       | 加急           | 標準      | 批量      | 最低天數 |
| -------------------------- | -------------- | --------- | --------- | -------- |
| Glacier Instant Retrieval  | 直接 GET，毫秒 | 不用取回  | 不用取回  | 90 天    |
| Glacier Flexible Retrieval | 1–5 分鐘       | 3–5 小時  | 5–12 小時 | 90 天    |
| Glacier Deep Archive       | 沒有           | 12 小時內 | 48 小時內 | 180 天   |

- 加急只適用 250 MB 以下的物件；解凍的副本過了指定天數自己消失，原物件還在冷層
- **Lifecycle 規則**：掛在桶上，對符合前綴或 tag 的物件按天數轉類別、過期刪除，天數從物件建立那天算（非目前版本則從被新版本取代那天算）；典型規則像「第 30 天轉 IA、第 90 天轉 Glacier、第 365 天刪除」
- Lifecycle 兩個坑，加一條收尾規則：
  1. **128 KB 以下預設不轉**：每轉一個物件收一次請求費，小檔轉了反而更貴
  2. **轉進去就要付最低天數**：第 90 天轉 Glacier Flexible、第 100 天刪掉，還是收 90 天的錢
  3. **開了版本控制的桶一定要加一條「非目前版本 N 天後過期」**，不然每次覆蓋都多留一份、永遠不刪
- 補充：
	- Life cycle 設定，可以針對每個儲存級別，並設定儲存天數。
	- 考試要背一個大概，從 Standard -> Standard IA -> Glacier 的順序。

## 六、S3 安全：四道門一把鑰匙

- 預設全鎖；要給外人東西，給鑰匙，不是開門。四道門各管一件事：
  1. **Block Public Access**（帳號層級，任何「對所有人開放」的 ACL 或 policy 都被擋下）：2023 年 4 月之後建的桶四個開關預設全開；官方建議額外開在帳號層級，帳號跟桶兩層取最嚴的生效
  2. **Bucket Policy**：掛在桶上（20 KB 以內），回答「這個桶讓誰做什麼」；跨帳號、給別的 AWS 服務、要加條件時靠它
  3. **IAM 身分政策**：掛在人、群組、Role 上，回答「這個人能做什麼」；只有它不夠跨帳號
  4. **物件靜態加密（SSE）**：2023 年 1 月起新物件自動用 **SSE-S3** 加密（AWS 自己的 AES-256 金鑰，免費）；要控管誰能解密、要有解密紀錄才升 **SSE-KMS**（金鑰在 KMS，代管或自建都行）；合規要求兩層加密才用 **DSSE-KMS**
- 同帳號任一邊 allow 就過，任一邊 deny 就擋；跨帳號要兩邊各自點頭；任何一道門寫了 deny 就擋下，三道都沒擋才拿得到物件
- **Presigned URL**：不是開門，是給鑰匙——用自己的權限簽一個網址，帶著自己的權限，到期失效。主控台最長 12 小時，CLI/SDK 最長 7 天；如果是用 Role 的臨時憑證簽的，Role 一到期網址就跟著死，效期寫再長也沒用
- 給外人東西的對照：客戶下載報告用**下載用的 Presigned URL**（不要把桶設公開）；使用者上傳檔案用**只能 PUT 那個 Key 的 Presigned URL**（不要給對方 access key）；另一個 AWS 帳號要讀用 **Bucket Policy 指定對方的 Role**（不要替對方建 IAM user）
- Bucket Policy 最常寫兩條：一條讓開發者 Role 只讀某前綴（`Resource` 寫到 `前綴/*`）；一條對所有人拒絕非 HTTPS 的請求（`Condition` 裡 `aws:SecureTransport` 為 `false` 時 Deny）——桶政策的 Allow 是加權限，IAM 已經給的權限，要收回只能用 Deny

## 七、S3 當 AI 的資料中心

- **RAG**（Retrieval-Augmented Generation）：先從自己的文件找相關段落，再交給模型回答；S3 放原稿，也能放向量——S3 是倉庫，向量索引是目錄，貨進了倉庫沒更新目錄，agent 就照舊目錄拿貨
- 檔案加、改、刪之後要按一次**同步（sync）**，同步是增量的，只動有變的檔：內容或 Metadata 變了才重新解析、切塊、向量化、寫進索引；新增檔案只處理新的；刪除檔案從索引裡移掉；沒變就跳過。不按同步，索引就停在上一次——沒有報錯也沒有警告，模型會拿著舊段落理直氣壯地講舊話
- 防索引過期三件事：同步要自動（排程或上傳事件觸發）；回答要附來源跟版本（物件的 Metadata 就在這裡用上）；原稿轉去 Glacier 之前先確認索引已經建好，不然重建索引要先等解凍
- 查詢量不大，向量先放 **S3 Vectors**（向量桶，原生存向量、做相似度查詢）；高查詢量、要混合檢索（向量相似度加關鍵字比對一起算分）、聚合、過濾才用 **OpenSearch Serverless**（貴）；中小型、資料本來就在關聯式資料庫裡的，資料庫單元再講
- 自架模型的推論節點會擴縮，每台開機都要載同一份幾十 GB 的權重：多節點跨 AZ 共享權重用 **EFS**（一份大家掛，新節點掛上去就能跑，正本仍放 S3）；要更高吞吐用 **FSx for Lustre**（AWS 代管的高效能平行檔案系統，給 HPC 跟機器學習用）；用 EBS 的話三台就要三份，權重更新要同步三次——這題只在自架模型時存在，專題用 Bedrock 按 token 算，權重在 AWS 那邊，不用管
- 金句：「S3 是倉庫，向量索引是目錄；貨進了倉庫沒更新目錄，agent 就照舊目錄拿貨」

## 一、核心實作：救回誤刪的檔、臨時連結分享

（分層評分：必做 70% / 進階 20% / 加分 10%）
全程在主控台點，不用開機器、不用寫程式，一個人三十分鐘做得完：

1. 必做 1–3：桶不公開，直接開網址被拒
2. 必做 4–5：臨時連結 5 分鐘後失效
3. 必做 6：刪兩次，第⼆次刪的是標記
4. 必做 7 與清理：舊版本 30 天後清掉
5. 進階：⽤ CLI 再做⼀次
6. 加分：強制只能走 HTTPS
- 繳交：必做五張截圖（沒公開的 AccessDenied、臨時連結過期、救回後打開是 v2、生命週期規則、清理後桶列表，各 14%）+ 進階三條指令的輸出（20%）+ 加分的 Bucket Policy（10%）
- 驗收重點：刪錯列照樣給分——說得出自己刪到的是什麼、為什麼剩 v1，這一步要學的是分辨「版本」跟「刪除標記」
