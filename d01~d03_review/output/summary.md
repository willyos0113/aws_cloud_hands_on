## D01:學習方法與 AI 家教

核心主軸:這門課的知識半衰期約 12 個月,重點不是背答案,而是建立「判斷、查證、記憶、除錯」的可遷移流程。

### 01 判斷資訊:來源、文件、該不該學

- **資訊來源分三層**:一手(官方文件、CHANGELOG、原始碼)跟服務同步更新,用來「下決定」;二手(部落格、書、課程,含本教材)約一年有效,用來「找路」;三手(懶人包、無出處的 AI 回答)當場可能就錯,只拿來找關鍵字後回一手查證。
- **過期教學六訊號**(中兩個先關掉):無日期或超過 18 個月、模組路徑對不上、用到已改名的 API、截圖與現況介面不符、留言反映跑不動且作者未回、多站一字不差的轉載。**訊號只能用來淘汰,不能拿來認證內容正確。**
- **判讀順序**:日期 → 路徑 → 留言 → 內文,前三步 30 秒做完,過關才值得細讀。
- **官方文件有三本**:How To(步驟,如 User/Developer Guide)、Reference(參數,如 API/CLI Reference)、Why(設計取捨,如 Well-Architected Framework)。三種問題對應翻不同的一本。
- 讀一頁文件:先看版本日期、提示框(Note/Warning),先跑官方範例,再逐欄讀參數表。
- **只有官方會提前公告服務生命週期**(範例:AWS CodeCommit 停收新客戶又於後續重新開放),因此需定期掃官方 What's New。
- 考證照可用 Exam Guide 的 Knowledge of 反推讀書清單;讀 CHANGELOG 要先看 Breaking changes、Deprecated、Removed,最後才看 Added。
- **技術該不該學的五個問題**(各有可查之處,兩題以上答不出來就再等半年觀察):誰在維護、有沒有生產採用、它取代了什麼、生命週期怎麼公告、學會之後帶不帶得走。
- 學習優先順序:**概念 > 通用工具 > 廠商包裝**,越靠右越容易被廠商關掉服務。`star` 數是歷史,`commit` 才是現在。
- 例外情況:太新(五問都答不出,先記錄日期六個月後重問)、公司已經在用(五問只拿來估風險)、一個週末能試完(直接做 demo 決定)。

### 02 跟 AI 一起學:陷阱與家教

- **三個陷阱**,解法都是回一手來源核對:
  - 知識截止日:模型不知道就會補一個「像的」答案,而不是說不知道。
  - 流暢不等於正確:錯答案與對答案語氣、格式一樣,唯一分辨法是去對一手文件。
  - 跳過理解:程式能跑但講不出「為什麼這樣寫」,沒改過、沒讀懂的每一行都是負債。
- **全課四步工作流**:①問地圖(要步驟、關鍵字、該翻哪本文件)→②對一手(逐一核對參數、跑官方範例)→③自己改(換值、換名、刪一行測試會不會壞)→④每行負責(交付物裡不能有解釋不了的行)。**課程規矩:程式碼從官方範例來,不從 AI 來。**
- 問法訣竅:要「地圖」而非「成品」、要「出處連結」而非「這樣對嗎」、要「若改 A 成 B 會怎樣」而非「幫我改」、要「當面試官質問我」而非「幫我解釋」。
- **驗證分界**:語法/格式/命名可以不驗證(錯了跑一次就看到);參數、預設值、限制、價格、配額、Region、版本、已改名 API 一定要驗證(錯了要花錢或跑不起來);架構建議屬灰色地帶,需比對 Well-Architected 再決定。
- **AI 家教的開場三件事**:我的程度、我的目標(含期限)、我已經知道什麼——少一件 AI 就會用平均值假設你。建議固定成一份檔案每次貼上。
- **六種問法骨架**:要地圖、要白話類比(並要求指出類比失效點)、要比較表(附出處)、要反問我(檢查是否真懂)、要挑毛病(扮資安稽核員質疑)、要出處(任何有數字的回答都要)。
- 好問法用三次以上可固定成 **Skill**(SKILL.md + references + scripts,每次對話先載入,不用重打指令)。
- **三不做**:不讓 AI 寫交付物(反過來讓它挑你的錯)、不接受看不懂的程式碼(講不出來就刪掉重問)、不用 AI 筆記取代自己寫的筆記。
- **AI 三種會失效的情況**:你不知道自己不知道什麼(需先讀目錄/考綱建立地圖)、需要肌肉記憶的事(看它做一百次不如自己做十次)、需要有人挑戰盲點(它傾向順著你講,最好找真人)。

### 03 留得住:記憶與除錯

- **主動回憶(active recall)**與**間隔重複(spaced repetition)**是高效用的兩種學習法;重讀筆記、畫重點、考前一晚集中複習則效用最低。
- 循環:讀 → 忘一點 → 用力想起來(這一步才是真正在練)→ 間隔拉長再重複。
- 課程設計的間隔安排:當天課後三問、隔週小測(不計分)、Stage 開頭回收舊單元、期末專題整合使用。
- **寫筆記兩原則**:用自己的話寫(每條至少一句是自己的判斷)、留下來源連結(連結失效本身就是過期訊號)。這也是不用 AI 生成筆記代替自己寫的原因——那是它的理解,不是你的。
- **除錯即學習**流程:
  1. 讀錯誤訊息:先看最後一行(型別與訊息)、往上找第一個自己寫的檔案(灰色是套件內部)、確認出錯當下變數值,三步做完才去搜尋。
  2. **二分法(binary search)縮小範圍**:註解掉一半,若「仍是同一個錯」代表錯在保留的那一半,繼續對半砍;若「錯誤變成別的錯」代表切壞了(通常砍掉了被依賴的定義),要把那幾行留著重切。規則:**每一步只改一件事**。
  3. **最小可重現範例(MRE)三條件**:最小(拿掉所有無關程式碼)、完整(別人貼上就能跑)、可重現(每次都出同一個錯)。
  4. **提問四段格式**:做了什麼、預期什麼、實際什麼(錯誤訊息原文)、已試過什麼——沒寫齊不回答,問 AI 也適用同一套。
  5. **30 分鐘規則**:到點就把問題交出去(寫四段貼討論區),等待回覆時去做別的事,不要死盯同一個錯——停損是把問題交出去的正確時機,不是放棄。

### 04 做得動:時間與環境

- **三個時間桶**:課堂(出席即可)、實作(需整塊 90 分鐘以上,每週至少 2 塊,用通勤/午休等零碎時間反而做不了)、證照自習(適合零碎時間)。
- **落後時的取捨順序**:①先停證照自習釋出時間 → ②只補本週實作(不追週週補) → ③舊內容靠課程的 Stage 回收機制 → ④專題開始後自然填洞。
- **Lesson 9(本單元驗收)**:在 50 分鐘內只靠官方文件建好整門課要用的環境,不准搜尋部落格教學。五項驗收標準各對應一本一手文件:雲端帳號 MFA(IAM User Guide)、預算告警(Cost Management User Guide)、CLI 多組態(`aws sts get-caller-identity --profile`,CLI User Guide)、Python 環境(venv/uv 文件、Boto3 Quickstart)、Git 與版控(Pro Git、GitHub Docs)。
- 多組態要點:`~/.aws/config` 與 `~/.aws/credentials` 各自維護同名 profile 區段(如 `course`),兩檔寫法不同但名稱要對應;常見卡點(如 `command not found`、`Unable to locate credentials`)可直接對應到文件的對應章節排查。
- **金鑰等同帳號密碼:不進 repo、不貼給 AI,只貼錯誤訊息。**

### D01 一句話總結
> AI 給地圖,文件給答案,你給責任。

## D02:DevOps 核心結構與 GitHub 基礎

核心主軸:「工具固定流程,文化決定流程」——DevOps 解決的是人與流程的問題,不是工具問題。

### 01 文化與自動化(CALMS)

- 開發(Dev)與維運(Ops)的目標天生衝突:Dev 被考核「功能出得快」、Ops 被考核「系統不要掛」,出事時互相甩鍋,不是態度問題,是結構性衝突。
- **CALMS 五面向**(Jez Humble 提出,評估組織 DevOps 成熟度):Culture(文化,同一結果共同負責)是地基,其餘四項都建在它上面;Automation(自動化)、Lean(精實,小批量快回饋)、Measurement(量測,部署頻率/修復時間等可見指標)、Sharing(分享,復盤公開不讓知識卡在個人)。
- **重要觀念**:沒有 Culture 的 Automation,只是更快地把問題丟過牆——工具再快,若沒有共同承擔結果的文化,出事後反而會因為流程摩擦而更慢(如部署前多開核准會議)。

### 02 CI/CD Pipeline

- **Pipeline 六階段**:Commit(合併)→ Build(建置)→ Test(測試)→ Scan(安全/授權掃描)→ Staging(測試環境)→ Production(正式環境),任一階段失敗即停止,不往下跑。
- **三個名詞差在自動化做到哪**:
  - CI(持續整合):自動跑到測試為止。
  - CD(持續交付,Continuous Delivery):自動到正式環境門口,上線前仍需人工核准。
  - CD(持續部署,Continuous Deployment):連上線那一下都自動,全程無人工核准。
  - **差別只有一件事:有沒有人工核准上正式環境**;很多團隊自稱 CD 其實只做到持續交付。
- **為什麼要常提交**:痛苦不是來自整合本身,而是來自累積——兩週才合併一次會遇到大量衝突,難以定位錯誤範圍;每天合併則衝突範圍小、當天可解。**擋在今天,不要擋在兩週後。**

### 03 Git 原理與指令

- **檔案三種狀態**:已修改(modified)→ `git add` → 已預存(staged)→ `git commit` → 已提交(committed,存進本地版本庫)→ `git push` 才離開電腦。Git 眼中的差異是「有沒有被記進快照」,不是「有沒有存檔」。
- **四層與資料流向**:工作目錄 → (add)預存區 → (commit)本地版本庫(.git)→ (push)遠端;反向則是 checkout / fetch / pull(pull = fetch + 自動合併)。前三層都在自己電腦裡,只有遠端在別人機器上。
- **三個常見誤會**:
  1. 以為 commit 之後東西就上雲了——其實只到本地版本庫,沒 push 前什麼都沒離開電腦。
  2. 以為 pull 跟 fetch 一樣——fetch 只下載不合併,pull 才會自動合併。
  3. 以為遠端是「正本」、本機是「副本」——Git 是分散式版控,每份 clone 都是完整歷史,遠端只是大家約定的集合點,離線也能 commit。
- **十個指令一張表**:add/commit/push/fetch/pull/merge/rebase/reset/revert/stash,各自對應「把什麼從哪一層搬到哪一層」;只有 push、fetch、pull 會碰到遠端。
- **reset 與 revert 的核心差異**:reset 把分支指標退回過去,後面的提交從歷史消失(改歷史,只能用在自己電腦裡、還沒 push 的提交);revert 是新增一個提交去反做某次改動,原本歷史都保留(加歷史,適用於已 push、他人已拿到的共用歷史)。`--hard` 是讓 reset 真正會弄丟資料的唯一旗標。
- merge / rebase / stash 概略:merge 分快進(fast-forward)與三方合併(three-way merge,產生雙親提交);rebase 把提交搬到對方尾巴重放讓歷史變直線;stash 把改動暫存起來但不是提交、不離開本機。
- **鐵則**:只在自己電腦裡的可以改歷史(reset/rebase),出了門(已推送共用)的只能加歷史(revert)。

### 04 GitHub 協作與規矩

- **Conventional Commits**:格式為 `type(範圍): 描述`,對應 SemVer(x.y.z):`fix` 對應 PATCH、`feat` 對應 MINOR、含 `BREAKING CHANGE` 或 `!` 對應 MAJOR。機器可依此自動產生變更記錄與版號。**diff 只講改了什麼,commit 訊息才講為什麼。**
- **Pull Request(PR)流程**:開分支(從 main)→ 提交(訊息照規範)→ 開 PR(描述寫四段)→ 審查(讀 diff)→ 檢查通過(自動測試/掃描)→ 合併。PR 的價值在合併前那段討論與審查的時間,不在按鈕本身。
- **PR 描述四段**:做了什麼、為什麼(連結 Issue)、怎麼測(可重跑的具體步驟)、風險或還沒做的。
- **Issue 與看板**:先開 Issue 討論要不要做,分支從 Issue 長出來,PR 描述寫 `Closes #編號` 合併後自動關閉。好處是每個改動都查得到「當初為什麼要做」。**訊息與描述是寫給三個月後的人看的,包括三個月後的你。**
- **分支保護(Branch Protection)三道閘門**:①一定要走 PR(不能直接 push main)②至少 N 個審查通過 ③狀態檢查(CI)綠燈。規則建立後預設就擋 force push 與刪除分支。
- 進階設定:`Dismiss stale approvals`(有新提交進來,舊核准作廢,避免核准後偷改)、`Include administrators`(管理員也要守規則,預設可跳過)。**Rulesets** 是較新機制,可多條同時生效,除分支外還能管理標籤與 commit 訊息格式(可強制 Conventional Commits)。
- **為什麼寫進工具而非寫進文件**:寫文件靠自律,趕時間第一個被跳過,出事後才發現沒守;寫進工具則第一次違規就被擋,趕時間也跳不過。

### AI 時代的責任

- 三個被打破的假設:**版權與授權**(AI 產出的程式碼授權歸屬未定)、**審查責任**(看不懂就 approve,誰負責?)、**機密外洩**(貼給 AI 的內容是否被留存或訓練?)。
- 今天就能做的:標明哪些是 AI 生成、看不懂的程式碼不進 repo(要求作者能解釋)、金鑰與客戶資料永遠不貼,只用公司核准工具。
- **立場**:「這段是 AI 寫的」不能當免責理由,按 approve 的人仍要負責。**AI 讓寫的人變快,沒有讓按的人變輕。**

### D02 一句話總結
> 工具固定流程,文化決定流程。

## D03:Docker 多系統兼容與 GitHub 多分支管理

核心主軸:讓「在我電腦上可以跑」這句話失去意義——建立可移植的映像,並管理好可安全合併的分支。

### 01 容器與映像

- **核心名詞**:kernel(核心)、VM(虛擬機,整台電腦含獨立 OS)、container(容器,借用主機核心的隔離環境)、image(映像,容器的唯讀範本)、layer(層,Dockerfile 每條指令產生的檔案變化)、cache(快取,輸入沒變就沿用舊層結果)。
- **VM vs 容器,差別只在核心那一層**:VM 每台各自帶一個 Guest OS 核心(較慢、較大但隔離乾淨);容器共用主機核心,只隔離看得到的東西(較快、較小但隔離較弱)。
- **三特性同一個原因**(共用核心):啟動快(不用開機,只是啟動被隔離的行程,但主機核心掛了全部容器一起掛)、映像小(不含 OS 核心,但映像跟主機架構綁定)、隔離較弱(需要強隔離仍要用 VM)。
- **常見誤解**:容器並非取代 VM 的二選一,雲端上容器多半跑在一台 VM 裡面——VM 負責跟其他租戶隔開,容器負責讓你的程式到哪都一樣。
- 代價:因為共用核心,`linux/amd64` 的容器不能直接在 `arm64` 主機上跑,程式必須與主機架構相容。

### 02 映像怎麼做、容器怎麼接

- **Dockerfile 四件事**:
  1. **多階段建置(multi-stage build)**:一個 Dockerfile 多個 `FROM`,建置階段可以裝編譯工具、跑測試(體積大沒關係),用 `COPY --from=建置階段` 只把成品搬到執行階段,最終映像不含編譯工具與測試檔。
  2. **順序影響快取**:某一層變了,它之後所有層都要重建,即使內容相同。因此依賴清單(`requirements.txt`)要先 `COPY` 並安裝,原始碼(常變動)放在最後一步 `COPY`,才能讓改一行程式碼時只重跑最後幾層。
  3. **非 root 執行**:建立專用使用者(`useradd`),最後用 `USER` 切換,避免容器以 root 執行——隔離本來就較弱,被攻破就是 root 權限。
  4. **最小基底且釘版本**:用 `python:3.12-slim` 而非 `python:latest`(標籤會被更新,三個月後可能指向不同版本);slim 夠用就不用完整版,但注意 alpine 連 git/bash 都不含。
- **快取規則只有一條**:某一層變了,它後面的每一層都要重建——排序要依「多久變一次」而非邏輯順序,依賴先於安裝,原始碼放在最下面。
- **容器對外只有兩條線**:
  - **Port 映射**(`-p 主機埠:容器埠`):主機在前;程式要監聽 `0.0.0.0` 而非 `127.0.0.1`,否則只有容器自己連得到。
  - **Volume 掛載**(`-v 卷名:容器路徑`):容器刪除後資料仍留在 Volume,是官方建議的持久化首選。
  - 資料持久化三種方式:Volume(資料庫/上傳檔案,官方首選)、Bind mount(開發時掛載原始碼即時改)、tmpfs(只存記憶體,容器停止即消失,適合機密/暫存)。
  - 排錯順序:**先查埠、再查路徑,然後才是程式本身。**
- **十二因子(Twelve-Factor App)Config 概念**:映像本身(程式碼、程式庫、執行環境)在各環境間保持不變,只有環境變數/設定(資料庫位址、金鑰)隨環境不同——這樣「建一次,處處跑」,環境差異收斂到設定層,就不會出現「本機可以、雲端不行」。

### 03 分支策略與合併衝突

- **Git Flow vs Trunk-Based**,差別是分支活多久:
  - **Git Flow**:master + develop 兩條長期分支,加 feature/release/hotfix 輔助分支,適合有明確版本節奏、需同時維護多版本的軟體。
  - **Trunk-Based**:一條 trunk 加短命分支(數小時到數天),未完成功能用 feature flag 藏起來先合併再打開,適合持續交付。
  - 判準三項:發布節奏(固定版本 vs 持續交付)、團隊規模(大且分工明確 vs 小到中且人人可推)、測試自動化(弱、靠人工驗 vs 強、CI 綠燈即可上)。**持續交付的 web 服務建議 Trunk-Based + 短命分支 + PR。**
  - Git Flow 作者本人在 2020 年反思:該模型是為 2010 年「需同時支援多版本」的軟體設計的,做持續交付的 web app 建議改用更簡單的流程。
- **合併衝突原理**:三方合併(three-way merge)比對共同祖先與兩端快照;若同一檔案同一部分在兩分支都被修改,Git 無法自動判斷該留哪一版,便用 `<<<<<<<` / `=======` / `>>>>>>>` 標記讓人決定。同檔不同段落則可自動合併。**衝突面積會隨分支存活時間累積,不是誰的錯。**
- **解衝突四步**:`git status` 找出 both modified 的檔案 → 打開標記決定留哪一版或合成新版(兩邊的業務意圖都要保留)→ 刪除標記並 `git add` → `git commit`(rebase 情境改用 `git rebase --continue`,可用 `git rebase --abort` 中途放棄)。
- **merge 與 rebase 的差異**:merge 產生分岔又匯合的合併提交,忠實記錄歷史,衝突一次解決,隨時可用;rebase 把提交搬到對方尾巴重放,歷史變一直線更好讀,但每重放一個提交都可能要再解一次衝突。**鐵則:不要對已經存在於你版本庫之外(已推送、他人已使用)的提交做 rebase。**

### 04 AI 環境與稽核實作

- **AI 開發環境的四個難題**(前三項有官方做法,第四項是取捨):
  - 依賴肥大(torch 等框架動輒數 GB):用多階段建置 + slim 基底,只裝需要的變體。
  - GPU 驅動綁定(驅動裝在主機核心層,容器內 CUDA 版本需與主機驅動相容):用 NVIDIA Container Toolkit,並記錄主機驅動版本。
  - 跨架構(amd64 映像無法在 arm64 主機直接跑):用 `docker buildx build --platform linux/amd64,linux/arm64` 建多平台映像。
  - 模型權重放哪:三種取捨——烤進映像(自帶但巨大、換模型要重建,適合小模型/離線)、掛 Volume(映像小、換模型不重建,但部署前要先放好權重,適合大模型/常換版)、啟動時下載(映像最小但啟動慢、依賴網路,適合雲端且有物件儲存)。
  - **一句話帶走:AI 映像的難題都是「容器借用主機」這件事的放大版。**
- **稽核清單七格**(前四格是瘦身、後三格是能否上線):階段(建置/執行分開)、順序(依賴先於安裝)、使用者(非 root)、基底(slim 且釘版本)、資料與埠(Volume 規劃、埠有文件化)、設定(未把 `.env` 或金鑰 COPY 進映像)、架構(跨平台時是否指定 `--platform`)。
- **稽核原則**:交出去的是量測數字(映像大小、首次建置時間、改一行後的重建時間),不是感覺;可讓 AI 扮演 SRE 稽核員找出多餘 Layer、快取失效點與 root 執行等問題。

### D03 一句話總結
> 容器不是輕的 VM,是借用核心的隔離行程;建置變慢多半是順序問題,不是機器問題;分支活得越久,合併越痛。

## 三天概念關聯

D01 → D02 → D03 是一條「先建立方法論、再學協作機制、最後應用到跨平台交付」的遞進路徑:

1. **D01 是後兩天的操作系統**:一手/二手/三手來源分層、判讀順序、AI 四步工作流(問地圖→對一手→自己改→每行負責)這套方法,直接決定了在 D02、D03 學 Git 指令、Docker 語法時該去查哪本文件、該信哪個答案、以及該怎麼用 AI 而不被 AI 的「流暢但錯誤」帶偏。D01 提到的除錯流程(讀錯誤訊息、二分法、最小可重現範例、30 分鐘規則)也是 D03 排查 port/Volume 連線問題、稽核 Dockerfile 問題時實際使用的思路。
2. **D02 的 Git 四層與十個指令是 D03 分支管理的地基**:沒有先搞懂「工作目錄→預存區→本地版本庫→遠端」與「只在本機的可以改歷史(reset/rebase)、出了門的只能加歷史(revert)」這條鐵則,就無法理解 D03 為什麼 Trunk-Based 要用短命分支、為什麼已推送的 feature 分支更新 main 要用 `merge` 而非 `rebase`。D02 的 PR/分支保護/Conventional Commits 也是 D03「合併回去的分支」要滿足的協作規矩。
3. **D02 的 CALMS 文化與 CI/CD 頻率概念延伸到 D03 的分支策略選擇**:D02 講「提交頻率決定整合痛苦程度」,D03 的判準表(發布節奏、團隊規模、測試自動化)其實是同一個原理在分支存活時間上的應用——分支越像「兩週才合併一次」,衝突面積越大。
4. **D02 的「AI 寫的程式碼誰負責」直接延伸為 D03 的稽核清單**:D02 建立「按 approve 的人要負責、看不懂的程式碼不進 repo」的責任框架,D03 的稽核清單七格與「AI 扮 SRE 稽核員」正是把這個責任框架具體套用到 Dockerfile 與映像品質上,而不是把稽核工作外包給 AI 自己判斷。

三天合起來的共同底層邏輯:**判斷來源與現況(D01)→ 把協作規矩寫進工具而非依賴自律(D02)→ 把環境與交付流程做成可重建、可量測、可稽核的東西(D03)**,目標都是讓知識與流程不依賴單一個人的記憶或自覺,而是被結構化地固定下來。
